# Wire protocol, version 1

[Developer documentation](development.md) · [Design and threat model](design.md)

Trew uses WebSocket connections. Text frames carry JSON control messages;
binary frames carry chunk bodies. Everything is readable by the server:
contents, paths, sizes, timestamps, device labels and routing metadata. TLS in
front of the server is required, because it is all that protects the device
credentials and the notes in transit.

This page is a reader's summary. The settled specification, with the reason for
each decision, is [plan/protocol.md](../plan/protocol.md); the executable
contract both implementations test against is `protocol-fixtures.json`
(generated by `scripts/protocol-vectors.py`) and `protocol-transcripts.json`.
Where this page and those disagree, they are right. The definitions in code are
[wire.go](../internal/wire/wire.go) and
[transport.ts](../client/src/core/transport.ts).

Protocol 1 is Trew's own. It was derived from Basalt Sync's protocol 7 by
removing the encryption: no root secret, data key, sealed paths or chunks,
entry authenticator, registrar session, recovery key or rotation. The two do
not interoperate, and each refuses the other at hello with `proto`, naming both
numbers.

The client normally uses one connection. Large uploads can use a temporary
second connection with the same device credential, leaving the main connection
available for note edits. Both use this protocol unchanged. Only the main
connection feeds metadata to the engine. After an auxiliary upload is
acknowledged, the client waits for a main-connection pong and reads all
preceding metadata before saving that upload's checkpoint. The auxiliary
connection never reports an applied cursor and closes at the end of the sync;
delivery remains conservative while the two sessions overlap.

Examples below are message shapes, not literal JSON: unquoted fields stand for
values, `?` means optional, and `...` omits fields already described.

## Design rules

Kept from protocol 7, numbered as there because code comments cite them:

1. Name outcomes explicitly: `have`, `want`, `ack`, and `err`.
2. Acknowledge a device's own writes without requiring it to download an echo.
3. Carry covered version ranges so clients can check stream continuity.
4. Derive sync decisions from state rather than a persisted "initial sync" flag.
5. Validate structure and limits before accepting content. The server also
   validates paths.
6. Retired: it versioned the wire separately from the encryption construction,
   and there is no construction.

## Handshake

A hello opens one of two sessions: a device session, or an invite redemption.

### Device session

```text
-> {op:"hello", id, proto:1, vault, deviceId, token, device, cursor, epoch?}
<- {res:"ready", id, proto:1, minProto:1, serverVersion, epoch, cursor,
    perFileMax, chunkMax, maxChunks, maxBatchBytes, maxFetchBytes}
```

`deviceId` identifies a paired device and `token` is its own random 32-byte
credential, unpadded base64url. The server keeps only the SHA-256 of the token
and compares in constant time. `cursor` is the last locally recorded metadata
UID, or 0. Its files may still be pending download; the separate `applied`
message confirms completed local application. `ready` advertises limits before
catch-up. A client refuses a `chunkMax` below its chunker's 192-byte floor at
this point, since every chunk it cut would be refused.

### The store epoch

`epoch` is an opaque name for the store's history. Every data directory has
one, and every `trew backup` snapshot is given a new one, so restoring a
snapshot always starts a new epoch. A device stores the epoch beside its cursor
and sends it in hello.

When the hello's epoch is not the store's, the server does not honour the
cursor in either direction: it replays the vault from uid 1, and `ready`
carries the store's epoch. The client discards its cursor as `ready` arrives
and reads the replay as a fresh listing: matching files agree, files that
differ are kept both ways as a conflict copy, files only the device holds are
uploaded, and nothing is deleted because the restored history lacks it. Then
it stores the new epoch.

A hello without `epoch` has its cursor taken as given, and a cursor ahead of
the store within one epoch is refused with `cursor`. That happens when a data
directory is copied back behind the server's back; the plugin's **Rejoin this
server** is the way out.

### Invite redemption

```text
-> {op:"hello", id, proto:1, vault, device, invite, deviceId, token}
<- {res:"redeemed", id, deviceId}
```

`invite` is the invite's 16-byte token, base64url. The joining client makes its
own `deviceId` (16 random bytes, base64url) and `token` (32 random bytes).
Before sending, it saves them as a pending pairing, with the server address,
the vault and the invite. On `redeemed` it replaces the pending pairing with
its device configuration, which no longer holds the invite; the server closes
the connection and the device reconnects as a device session. On a refusal it
deletes the pending pairing, so nothing is left saved. On a lost reply it keeps
the pending pairing and retries with the same `deviceId` and `token`.

The server redeems in one transaction: it spends the invite and inserts the
device row, or does neither. A retry from the device that spent the invite,
with the same id and token, is answered `redeemed` again, even after the invite
has expired. Every refusal (an unknown, spent, expired or cancelled invite, an
existing device id, an id under the reserved `mcp:` prefix, a vault this server
does not serve) is the same `auth` with the same message, and writes nothing:
a refusal never spends the invite. A request's own shape is named instead,
because it says nothing about the vault: a bad device id or name is `badname`,
and a token that is not 32 bytes is `badentry`.

### Validation and compatibility

Only **protocol 1** is supported. A refusal names supported protocol numbers,
not the server release; `serverVersion` is disclosed only after a credential
matches. Vault and device names are bounded at 64 bytes and reject control
characters. Device IDs are base64url, up to 64 characters. The order in which
a hello's refusals are checked, so that nothing before the credential depends
on the vault, is in [plan/protocol.md](../plan/protocol.md).

## The invite string

```text
trew1i_ <base64url( version=1 || token[16] || len(url) || url || len(vault) || vault || crc32 )>
```

Each length is one byte. The CRC is IEEE CRC-32 over everything before it,
big-endian. The base64url is unpadded and canonical, the URL is canonical
`ws://` or `wss://` with no trailing slash, and the vault is 1 to 64 bytes.
Decoders refuse anything else rather than normalising it, so both
implementations accept exactly the same strings. The `invite` section of
`protocol-fixtures.json` pins the format.

A device formats the string from the token in `invited`, with its own server
address and vault. The plugin shows it as a QR code of
`obsidian://trew?invite=<string>`.

## Request ids

Requests expecting replies carry an integer `id` from **1 to 2^32-1**, unique
among requests in flight. This applies to hello, put, putmany, get, fetch,
resend, history, deleted, devices, rename, revoke, invite, uninvite, and
applied. Replies and request-specific errors echo the ID.

Missing or invalid IDs cause `protostate` and end the session. Clients also end
a session on an unknown reply ID. Unsolicited batches, caught-up notices, pings,
and connection-closing errors are handled separately from request replies.

## Catch-up

```text
<- {res:"ready", ...}
<- {op:"batch", from:120, to:139, entries:[...]}
<- {op:"batch", from:140, to:151, entries:[...]}
<- {op:"caught-up", cursor:151}
```

`batch` is the only message delivering entries; a live change is a batch of one.
Its range covers `from <= uid <= to`. Clients require `from == cursor + 1`.
Purge can leave holes, so a covered range need not contain every UID.

The server orders batches by UID, including concurrent commits. A device's own
write is delivered to it as an empty batch that advances its cursor. Live
changes during catch-up are held and delivered in order afterwards.

Continuity checks detect malformed ordering but do not prove that the server
supplied every entry in a covered range.

When a device has overlapping live sessions, delivery uses their lowest
confirmed applied checkpoint. If any session has not confirmed a checkpoint,
the device's applied checkpoint is unknown. A connection alone is not evidence
that notes reached its filesystem.

## Paths

Every `path` and `prev` is the plaintext vault-relative path, `/`-separated,
NFC-normalized UTF-8. The server keeps Obsidian's keyspace: it refuses with
`badpath` a path that is empty or over 1,024 bytes, has a segment over 255
bytes, is not valid UTF-8 or not NFC, has a control character, a no-break space
(U+00A0 or U+202F) or a backslash, has a leading or trailing `/` or an empty
segment, has a `.` or `..` segment, has any segment beginning with a dot, or
carries the staging mark `.trew-tmp-`. The message starts with the reason code,
as in `dotprefix: the path has a segment that begins with a dot, ...`, so a
client reads the reason as the text before the first colon and shows it.

A create, or the destination of a move, whose case-folded key equals that of a
different live path, file or folder, is refused with `collision`, and the
message names the live path. The fold is Unicode full case folding, pinned in
the fixtures, so `Straße.md` and `STRASSE.md` collide. A rename that changes
only case is allowed, and deleted paths never collide. The full rule set,
including directory prefixes and batches, is in
[plan/protocol.md](../plan/protocol.md#paths).

A client shows either refusal as a stranded path with its reason, and keeps the
file.

## Writing a file

```text
-> {op:"put", id, path, meta:{size, ctime, mtime, folder, deleted, prev?},
    chunks:[h1,h2,h3], base, prevBase?}
<- {res:"want", id, chunks:[h2]}
-> body frame for h2
<- {res:"ack", id, uid:152}
```

When all bodies already exist, the server records the entry and returns
`{res:"have", id, uid}` instead. Both `have` and `ack` mean the content and
entry are durable.

- A chunk's name is the 64-character lowercase hexadecimal SHA-256 of its raw
  bytes. The server hashes every body it receives and refuses a mismatch.
- `size` must equal the sum of the chunks' raw lengths. The server checks this
  at commit and refuses a mismatch with `badentry`.
- Bodies are matched to requested names by hash. A bad body mid-upload ends the
  session because the remaining frame count can no longer be trusted.
- Empty files, folders, and deletions have no chunks and a size of 0; `chunks`
  is always an array.
- `prev` identifies the former path for a file rename. This is separate from
  the `rename` operation that changes a device label.
- Errors rejecting an individual request normally leave the session usable.
  See the error table for cases that close it.

Clients must dispatch unsolicited batches independently while awaiting replies.
The server pings idle sessions and allows an upload in progress to finish during
graceful shutdown. Idle sessions receive a retryable shutdown error.

## Chunk bodies on the wire

A body frame is one binary WebSocket frame: a marker byte, then the payload.

```text
byte 0      marker: 0 = raw, 1 = raw deflate (RFC 1951)
bytes 1..   payload
```

A sender uses marker 1 only when the deflated payload is shorter, so a frame is
at most `chunkMax + 1` bytes. The receiver refuses a longer frame before
inflating anything, bounds the inflation at `chunkMax` as it goes, refuses an
empty chunk, then hashes the raw bytes against the name. A frame over the bound
or one that inflates past `chunkMax` ends the upload with `toolarge`; any other
frame the decoder refuses is `badchunk`. The server stores raw bytes.

Deflate is a wire encoding only. Names are over raw bytes, so the two
implementations' deflate output need not agree byte for byte, and changing the
codec can never change a chunk's identity. Framing lives at the transport
boundary: the engine and everything above it see verified raw chunks, never a
marker byte. The `frames` section of the fixtures pins the edge cases.

## Writing many files at once

```text
-> {op:"putmany", id, entries:[{path, meta, chunks, base, prevBase?}, ...]}
<- {res:"want", id, chunks:[h1,h2,h3]}
-> body frames
<- {res:"acks", id, results:[{uid:152}, {uid:153}, {code, msg}, ...]}
```

A batch contains at most 256 entries. Four budgets apply, stated separately:
the raw bytes (the summed declared sizes, at most `maxBatchBytes`), the frames
on the wire (one per chunk, each at most `chunkMax + 1`), the control message
(one text frame within the post-handshake read limit), and the aggregate per
request, which is the raw budget. Clients split batches and use `put` for a file
whose own size exceeds the batch budget.

`results` has one slot per input entry. A refused entry does not reject the
others. An empty batch is `badentry`; too many entries is `toolarge`. All other
`put` rules apply.

### Conditional writes

Every `put` and `putmany` entry includes `base`: the UID of the target version
used to prepare the write. Zero means the target has no live entry, including
recreation after a deletion. A nonzero base must match the current logical head.
A rename also includes `prevBase`, which must match the source version.
A rename creates a logical deletion at its old path with the same new UID.

The server checks both preconditions inside the append transaction, after any
body transfer. If either changed, `stale` refuses that entry without committing
it. Other entries in a batch can still succeed. The client processes incoming
metadata and reconciles before trying again, preserving overlapping edits as
visible copies. It does not retry the same stale decision blindly.

`base` and `prevBase` are request preconditions, protected only by the TLS
connection. They are not stored history fields. This protects honest concurrent
writers; it does not make the server an independently verifiable history
authority. A lost reply can follow a successful commit, so clients reconcile
ambiguous results too.

## Reading a file

```text
-> {op:"get", id, uid}
<- {res:"chunks", id, uid, size, chunks:[h1,h2,h3]}
-> {op:"fetch", id, chunks:[h2]}
<- {res:"bodies", id, count:1}
<- body frame for h2
```

A fetch can combine chunks from several files within `maxFetchBytes`. The
response announces exactly the number of frames to follow, in requested order,
each framed as above. If any requested body is unavailable, it returns
`nochunk` without sending a partial set. Hash failures are quarantined before
announcing bodies. The client decodes each frame, bounded by `chunkMax`, and
hashes the raw bytes against the name; a frame that does not decode or a hash
that does not match ends the session.

A missing UID returns `nouid`; a folder or deletion returns `nocontent`.
A zero-byte note has a valid empty chunk list. Clients check the listed size
against the assembled bytes before applying content.

## Deleting

A deletion is an entry with `deleted: true`, not an absent path. Its record
remains available to catch-up and recovery even if older content is later purged.

## Repairing a body the server has lost

`resend` repairs missing stored content without creating a note version:

```text
-> {op:"resend", id, chunks:[h1,h2]}
<- {res:"want", id, chunks:[h2]}
-> body frame for h2
<- {res:"resent", id, stored:1, missing:0}
```

It is an upload path: the bodies are framed and checked exactly as for `put`.
Only names referenced by committed entries in the vault are eligible; others
return `nochunk`. No UID or entry is created. `missing` counts requested bodies
still absent after the attempt; it does not measure unavailable history the
client never offered. Server-side `verify` is required to assess the store as a
whole.

## Recovery

| Request | Reply |
|---|---|
| `{op:"history", id, path, before?, limit?}` | `{res:"history", id, path, entries}` |
| `{op:"deleted", id, before?, limit?}` | `{res:"deleted", id, entries, more}` |

History returns versions newest first, including deletions; `before` pages
backward. An empty history does not distinguish an unknown path from purged
history.

Deleted lists the latest deletion for each path, suppressing file renames and
bounding each page at 1,000. `more` indicates another page. `restorable` names
the newest content-bearing UID or is 0 when none remains.

There is no restore wire operation. A client reads a historical version,
checks it against the history it was listed in, writes a local copy, and
ordinarily uploads it as a new version.

## Devices and invites

```text
-> {op:"devices", id}
<- {res:"devices", id, devices:[{id, name, createdAt, lastSeen, online, applied}],
    invites:[{invite, label, expiresAt}]}

-> {op:"rename", id, name}           <- {res:"renamed", id, name}
-> {op:"revoke", id, deviceId}       <- {res:"revoked", id, deviceId, self}
-> {op:"invite", id, ttlMs?, label?} <- {res:"invited", id, invite, token, expiresAt}
-> {op:"uninvite", id, invite}       <- {res:"uninvited", id, invite}
```

Every device session may use these. The operator has the same through
`trew invite`, `trew devices`, `trew revoke` and `trew uninvite` on the server
host, which go through a private control socket while `serve` runs.

**Invites.** `invite` in a listing, in `invited` and in `uninvite` is the
invite's id: 8 random bytes, base64url, minted with the invite and not derived
from its token. Nothing in any listing can redeem an invite; `token` appears
once, in `invited`, to the device that asked. `ttlMs` of 0 or absent is the
one-hour default, anything above an hour is clamped to one hour before it is
converted, and a negative one is `badentry`. `expiresAt` is null only for an
invite that never expires, which only `trew invite -ttl 0` on the server can
make. A label is at most 64 bytes with no control characters. `uninvite` of an
id that is unknown, spent, cancelled or expired is `badentry`. A backup carries
no outstanding invite, so restoring an old copy cannot revive one that has
since been used or cancelled.

**The first device.** `trew serve` on a store with no devices and no
outstanding invite mints one invite and writes it, mode 0600, to
`<data>/first-invite` (or `-invite-out FILE`), one line per address the server
can name. It logs the path and the expiry, never the string, because a
container log is not a private place.

**Revoke.** The row is deleted and the device's sessions are taken out of the
fan-out in one hold on the commit lock, which every mutation and broadcast
also takes, so no later commit reaches them and no mutation they have in
flight can commit. Revoking a device cancels, in the same transaction, the
invites it issued. The last device may be revoked; the way back is
`trew invite` on the server. `self` is true when a device revoked itself, and
the reply is then the last frame on the connection. A device id the vault does
not have is `nodevice`. Revocation cannot erase what the device already holds.

**Rename** changes only the calling device's row. An empty or invalid name is
`badname`. No content version or UID is created, and historical device labels
and existing conflict filenames are unchanged.

A stored device row holds its ID, readable name, credential hash, creation time
and last-seen time; the listing omits the hash. IDs establish identity; names
need not be unique. There is no fixed limit on devices or authenticated
connections. Connection-level `busy` indicates pre-authentication admission
pressure or shutdown and can clear by waiting. An interrupted pairing can leave
an unused device row, which remains until revoked.

## Which clients may connect

Non-browser clients may omit Origin. Cross-host browser origins must match
`app://obsidian.md`, `capacitor://localhost`, `http://localhost`, or an explicitly
configured `-allow-origin`. The WebSocket library also accepts an Origin whose
host matches the request's Host. Every connection still needs a valid credential
or invite in hello. Rejected origins are logged with an operator hint.

## Errors

```text
<- {res:"err", id?, code, msg, retryable, retryAfterMs?}
```

`code` is machine-readable; `msg` explains the problem. Request errors echo the
ID. Unsolicited errors describe why a connection is closing. `retryable` says
whether reconnecting later may help; clients retain defaults for malformed
frames missing that field. `stale` requires a new reconciliation decision,
not an automatic retry of the unchanged request.

| code | meaning | retryable | session |
|---|---|---|---|
| `proto` | Unsupported protocol number. | no | ends at hello. |
| `auth` | A bad credential, an invite that cannot be redeemed, or an operation not allowed. | no | ends at hello, otherwise rejects the operation. |
| `cursor` | Client is ahead of server history within one epoch. | no | ends. |
| `busy` | Pre-authentication admission pressure or shutdown. | yes | ends with a delay hint. |
| `protostate` | Unexpected message or state, or invalid framing. | no | generally ends. Unknown ops and invalid history pagination reject that request. |
| `badchunk` | Invalid name, a body frame that does not decode, or a hash mismatch. | no | ends for bad bodies mid-upload, otherwise rejects the request. |
| `badpath` | Path refused by the path rules; the message starts with the reason code. | no | rejects the entry. |
| `collision` | Another live path has the same case-folded key; the message names it. | no | rejects the entry. |
| `stale` | Target or rename source changed before commit. Reconcile and retry. | no | keeps the session; batched refusal affects only that entry. |
| `badentry` | Invalid entry, including a size that is not the sum of its chunks, or a request incompatible with current state. | no | rejects the request. |
| `badname` | Invalid name or device ID. | no | ends at hello, otherwise rejects the request. |
| `toolarge` | A limit or declared size was exceeded, or a frame over its bound. | no | ends if upload framing cannot continue, otherwise rejects the request. |
| `nospace` | Storage capacity exhausted. | yes | ends during upload. |
| `nouid` | Version does not exist. | no | request rejected. |
| `nocontent` | Requested version is a folder or deletion. | no | request rejected. |
| `nochunk` | Content unavailable. | no | request rejected without partial fetch bodies. |
| `nodevice` | Device ID does not exist. | no | request rejected. |
| `internal` | Server fault; nothing committed. | yes | ends during handshake/catch-up, otherwise rejects the request. |

`busy` includes a retry delay for admission pressure or shutdown. Numeric limits
are in the [server reference](server-reference.md#ceilings).

## Device delivery confirmation

```text
-> {op:"applied", id, applied:cursor}
<- {res:"applied", id, cursor}
```

Only device sessions may confirm delivery. A client sends this after a
successful sync pass saves its files and index, with no pending work, refusals,
exclusions, held-back changes, or retries. Merely loading metadata or opening
an inspection connection does not confirm delivery. The server checks that the
checkpoint is nonnegative, no newer than its own history, and does not move
backwards on that connection. An invalid checkpoint returns `badentry`.

Each row returned by `devices` includes `online` (boolean) and `applied`
(nonnegative cursor or null). A connected device with `applied >= target` has
reported applying all changes through that target. Null means unconfirmed.
Receipts are held only in memory for the connection's lifetime; disconnect and
server restart clear them. These are trusted-device claims used for display,
never authorization, a backup guarantee, or permission to delete history.
