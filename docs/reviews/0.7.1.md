# Basalt 0.7.1 code, UX, and documentation review

Reviewed September 9, 2026, against commit
`920324c6e3313cd0c56d02425963e46b2260bb01` (plugin and CLI 0.7.1).
Server 0.7.0 uses the same protocol, 6.

**Update, September 10:** the implementation pass addresses the findings below.
See [fixes, verification, and remaining acceptance work](0.7.1-fixes.md). This
report preserves the original diagnosis and baseline results.

**The reviewed 0.7.1 release has a blocking concurrency defect.** Three devices can edit
different lines of a note, converge, and report successful sync while one
device's edit is absent from every current copy. That edit remains recoverable
from server history. This happened with an ordinary, honest server and trusted
devices; it does not require a hostile server or unsupported shared filesystem.

The other findings are narrower. The existing tests pass, but newly added
reproductions expose missing coverage. Production code and installed copies
were not changed during this review. Four documentation pages were corrected.

The review focused on the shared merge/index/transport paths, simultaneous
writers and reconnects, server append/replay/delivery behavior, CLI history and
argument contracts, filesystem change detection, plugin editor integration and
recovery UI, and the documentation's accuracy and audience.

### R071-01: successful convergence can omit an independent edit

Relevant code: [batch acceptance](../../client/src/core/engine.ts),
`acceptBatch` at line 1125; upload acknowledgement handling at line 2194;
[sync decisions](../../client/src/core/index-state.ts), line 233;
[server commit](../../server/internal/server/session.go), line 1834;
[store append](../../server/internal/store/store.go), line 693.
Line numbers in this report refer to the reviewed commit.

The deterministic reproduction starts A, B, and C from the same three-line
note. Each edits a different line. All prepare uploads before receiving the
others' changes. B's upload completes first and B records its own version as
its synced ancestor; C and A's stale uploads then commit. Their replies are
held until the competing broadcasts have arrived. These are explicit test
gates around real transport operations, not timing sleeps or modified server
behavior.

After twelve settlement rounds, every device has identical files and
`deliveryReady === true`. Their note contains A and C's edits, but B's edit
is absent from all visible files, including conflict copies. Reading history
still finds B's edit. One captured history illustrates the result:

| Server UID | Contents relative to the original |
|---|---|
| 1 | Original |
| 2 | B's edit |
| 3 | C's edit |
| 4 | A's edit |
| 5–6 | A + C; B's edit missing |

An ungated three-device offline/reconnect test also loses an edit. A separate
same-line rewrite test passed an earlier run and failed a later one with one
writer's text missing; it is useful scheduling coverage, but the deterministic
disjoint-edit test is the stable reproduction to start with.

The server serializes appends and broadcasts correctly, but accepts a write
without checking whether the path changed since the writer based its decision
on it. The client retains the latest remote entry per path. Its late-ack check
handles some two-writer races, but a later UID need not contain an earlier
writer's edit. A client whose local bytes equal its recorded ancestor can then
download that later branch without merging or preserving its own branch.

**Recommended fix:** conditional append against the expected current version
of the path, checked atomically with the append. A stale writer must fetch and
reconcile the new head before retrying. Apply the rule to individual and
batched uploads, deletions, and both names involved in a rename. A partial batch
or lost acknowledgement must remain recoverable. Bind the new precondition to
the authenticated request metadata as appropriate; a client-only observation
just before sending leaves the same race open.

This is a proposed protocol change, not a verified fix. Keep the regression
red until every edit survives under the acceptance cases below. History makes
recovery possible, but silently requiring history recovery is not successful
sync. Purging history also removes that fallback.

### R071-02: BOM decoding gives replacement the wrong baseline

[Merge handling](../../client/src/core/engine.ts), lines 3327 and 3386, decodes
UTF-8 with the default BOM behavior, then re-encodes the decoded local text to
construct the replacement's content digest. The decoder removes a leading BOM,
so this digest no longer identifies the original local bytes. The preserving
adapter correctly treats the mismatch as an intervening edit.

Two devices making disjoint edits to a BOM-prefixed Markdown note produce three
visible files instead of one. Both edits survive, but the conflict copies are
unnecessary. A scratch-only change to preserve the BOM with `ignoreBOM: true`
made this targeted test pass; that change was reverted after diagnosis.

Use the original `mineBytes` for the comparison digest and define consistent
BOM-preserving merge behavior. Cover BOM plus CRLF through the complete engine
and both adapters; the existing adapter-only BOM tests do not exercise this
decode/re-encode path.

### R071-03: the hash cache misses metadata-preserving edits

[`needsRehash`](../../client/src/core/index-state.ts), line 331, trusts unchanged
size and rounded modification time. The plugin's create/modify event handlers
in [main.ts](../../client/src/plugin/main.ts), line 313, schedule a scan without
invalidating the particular file's cached content.

The reproduction syncs `BEFORE\n`, replaces it with same-length `AFTERS\n`,
and restores the original mtime. Repeated sync passes leave the other device
with `BEFORE\n`. This requires preserved or indistinguishable timestamps; it
does not establish a failure for every normal editor save. Backup tools,
generators, and file copies that preserve timestamps make it a realistic edge.

Carry dirty paths from filesystem/Obsidian events into cache invalidation.
Use stronger available Node filesystem identity/change information as an
additional signal, and provide an explicit content-verification pass for
changes hidden by metadata. Retain fallback scans for missed events. Hashing
the entire vault on every keystroke would be the wrong performance tradeoff.

### R071-04: older CLI history is not discoverable

[`cmdHistory`](../../client/src/cli/cli.ts), line 1999, caps requests at 500
and calls `client.history(path, { limit })`. The shared argument parser accepts
`--before`, but this command ignores it. A three-version fixture returns UID 3
for both `history --limit 1` and `history --limit 1 --before 3`.

The docs currently describe `--before` for deleted-file browsing, not history;
the defect is the absence of a history paging route and silent acceptance of an
ineffective flag. Older versions still exist, and restore can locate an older
version if its UID is already known.

Forward and validate the cursor, expose how to request the next page in text
and JSON, and reject options that have no meaning for a command. Test a history
larger than one server page, including tombstones and purged history.

### R071-05: restore confuses server upload with device delivery

[`restoreAndSend`](../../client/src/plugin/main.ts), line 1499, sets `sent`
after `serverHasOurs`. [`describeRestore`](../../client/src/plugin/history.ts),
line 63, turns that into a claim that the restored file reached other devices.
No receiving device's applied checkpoint is checked, so an offline phone still
gets described as having received it.

Say “Uploaded to server. Other devices will receive it when they sync.” Use
the separate delivery receipts only for an actual device-delivery statement.
The user guide was corrected here; the runtime message remains open.

### R071-06: history rows are pointer-only controls

[`HistoryModal.renderList`](../../client/src/plugin/history.ts), line 231,
creates clickable `div` elements without focusability, keyboard handlers, or
selection semantics. The action buttons are accessible, but Tab cannot reach
the versions to choose an older one.

Use semantic buttons or a keyboard-operable listbox, expose the selected item,
and preserve focus when paging or rebuilding the list. Verify keyboard-only
operation and a mobile screen reader in the real app. This review established
the missing DOM behavior; it did not run a native screen-reader session.

### R071-07: an unknown overlapping session is omitted from delivery status

[`Hub.deviceStatus`](../../server/internal/server/delivery.go), line 29, takes
the minimum of known applied checkpoints for a device's live sessions but
ignores sessions that have never reported one. The reproduction connects B,
records applied UID 1, then connects B again with cursor 0 while its old
connection remains open. The device list still reports applied UID 1.

This concerns duplicate credentials or overlapping reconnects, not two
normally paired devices with separate credentials. A reconnect to the same
unchanged local storage may already have those bytes; this is not evidence of
another data-loss bug. It does contradict the conservative interpretation of
a connection-scoped delivery claim when a replacement has not confirmed it.

Define the aggregation rule explicitly: an unknown active sync session makes
the device unknown, or one authoritative connection generation supplies its
status. Account for read-only inspection sessions when making that choice.
Keep receipts advisory; do not use them to decide that history is safe to purge.

### R071-08: usage errors have inconsistent exit codes

[CLI dispatch](../../client/src/cli/cli.ts), lines 161–245, returns 2 for parser
errors but catches later argument-validation errors as operational failures
returning 1. `basalt sync unexpected-vault-argument` demonstrates the mismatch
with the documented “invalid arguments: 2” contract.

Validate usage before operational dispatch, or use a typed usage error. Cover
unknown options, extra positional arguments, missing required arguments, and
flags used on the wrong command without starting a server for every case.

### R071-09: the Compose purge example could not complete

The previous [operations guide](../server-operations.md#purge) backed up to
`/data/before-purge`. The public backup command calls
[`RefuseSamePlace`](../../server/internal/store/backup.go), line 840, and
refuses a destination inside the live data directory. Its documented backup
step therefore failed before verification or purge.

The corrected example mounts a separate host backup directory at `/backup`
for backup, verification, and purge. It specifies permissions, a fresh backup
name, stopping on errors, and copying the backup off the server. A real CLI
test confirms that the nested destination is rejected and an external one
works. The full Docker maintenance procedure was not rerun in this review.

## Architecture: strengthen ordering, keep the scope

These findings are not all one kind of bug. R071-01 is a branch-ordering issue;
R071-02 and R071-03 concern byte identity and cache validity; R071-05 and R071-07
concern what a status statement proves. CLI and accessibility defects are
ordinary interface gaps.

Keep the personal-device threat model, encryption, staged recovery, manual
lock recovery, and one-server design. Trusted devices can still write
concurrently, disconnect after a commit, and reopen from older local state.
Calling those situations unsupported would remove the core product use case.

The existing server sequence and transaction boundaries make conditional
writes a smaller starting point than CRDTs or replacing the whole sync engine.
The authenticated `parent` field alone does not enforce ancestry today. The
documented limitation around malicious replay does not explain away this
honest-server failure.

Keep separate tests for transport progress, durable storage, edit preservation,
and user-visible delivery. Passing any one does not establish the other three.
The Go race detector checks memory access, not logical lost-update races.

Useful existing foundations include the shared core, validation before
applying received batches, durable chunks before metadata acknowledgement,
serialized binary exchanges, bounded slow-peer queues, and non-overwriting
restore. The existing rename/delete/edit reproduction also preserved the edit
and converged in this review. Those are reasons to repair the specific missing
contracts rather than replace all of the implementation.

## UX priorities, including phones

1. **Make conflicts actionable.** Add “Review conflicts (N)” with the original
   and preserved paths, timestamps, a readable comparison, and keep/merge
   actions. Recheck the selected versions before applying a choice. Counts
   and transient notices are insufficient once the notice disappears.
2. **Add a bounded activity log.** Show file, operation, time, and result with
   search and error/conflict filters. Retain a limited recent log across
   restarts, never note bodies or secrets. Make export redact sensitive paths
   by default. Official Sync's documented log disappears on app exit; a small
   retained log would improve mobile troubleshooting beyond that behavior.
3. **Keep the default settings clean.** Preserve the simple Sync now / Browse
   deleted view. Put log, pause/resume, history, and review actions behind the
   compact status control. Show “Waiting for phone” only when receipts support
   it, with an explicit distinction between offline and unknown.
4. **Bound history previews.** The current history source decodes every version
   as text, and the modal builds the full text/diff. Use type-aware previews:
   readable text within a limit, attachment metadata for binaries, and an
   explicit way to open larger content. A large PDF should not become a huge
   text rendering on a phone. Allocation/crash behavior was not measured here.
5. **Preview exceptional bulk work.** For a populated vault's first pairing or
   a large deletion, show what will upload, download, and remain as copies.
   Keep normal note editing free of confirmations. Derive a guard from the
   actual operation, not an arbitrary percentage copied from another plugin.

Validate these in Android Obsidian with long filenames, light/dark themes,
large text, the keyboard open, offline resume, and TalkBack. Desktop mobile
styles and screenshots do not establish native Android behavior.

## Performance and maintainability

Fix preservation before further latency work. Then measure saved edit to
remote persisted bytes and visible editor update separately, with p50/p95
latency, on two and five clients and on the actual phone.

| Candidate | Reason to investigate | Constraint |
|---|---|---|
| Dirty-file work before a full scan | Saved edits currently schedule scans of the vault | Pair with R071-03 cache invalidation; keep recovery scans |
| Smaller transfer batches while a note is active | An in-progress binary exchange can delay the next small note | Preserve serialization of headers, bodies, probes, and replies |
| Faster initial metadata catch-up | Replay traverses historical entries, even when many versions describe one path | Profile large histories first; a snapshot protocol must preserve ordering and deletion semantics |
| Bounded history diff/preview work | Unbounded strings and DOM work are costly in the mobile renderer | Preserve access to the complete version through an explicit action |

These are candidates, not measured speed gains. The review did not run a new
head-to-head benchmark against official Sync. Removing fsyncs, compare-before-
write checks, or protocol awaits would weaken correctness, not establish speed.

Several large files mix transport/state machinery, user flows, and long
incident narratives. Extract cohesive pieces when fixing their behavior:
history/pairing/device settings from plugin `main.ts`, argument validation from
CLI dispatch, and explicit conditional-write state from the engine. Keep short
invariant comments and links to regressions. The engine's batch-exchange catch
comment currently says no write committed, although a lost reply can follow a
commit; comments must describe ambiguous outcomes correctly. The concurrency
test header's pre-request-ID description is stale too.
