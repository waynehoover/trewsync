## Findings

### A. Internal contradictions that must be resolved before anything is frozen
1. **`auth` vs `token` in invite redemption.** PLAN M1.1 and M2.3/M2.5 say redemption hello carries `{invite, deviceId, auth, device}`. protocol.md's handshake says `{op:"hello", ..., invite, deviceId, token}`. Two lanes implementing a "frozen" document from two different field names is exactly the failure the freeze is supposed to prevent.
2. **`scope` on MCP tokens.** mcp-tools.md gives tokens `scope: read|write` and a `--scope` flag. PLAN §2.3's credential table and §3.3's `mcp_tokens` schema have no scope column. Pick one.
3. **Search index sync vs async.** §2.5 says the FTS index is "maintained inside the commit transaction". mcp-tools.md's `vault_status` returns `index: {fresh, indexedHead}` and "`index.fresh` is false while a rebuild is running". A transactional index is always fresh by construction; the `fresh` field only makes sense in an async design. See F4.
4. **Cross-runtime byte equality.** §2.2 celebrates deleting `compression-golden` because "codec output never affects identity". M7.1 then requires "a fixture of chunk boundaries generated by the TypeScript implementation ... so both sides cut identically and dedup holds". That is a harder cross-runtime pinning requirement than the one being removed, reintroduced 6 milestones later.

### B. Substantive changes

**F1. Delete the Go engine port (M6 + M7). Replace with a server-owned folder.**
9,000 lines of Go (engine 5,519 + vaultfs from a 3,445-line adapter + merge + chunking + index journal) to produce a second implementation of the one component that decides what happens to someone's notes, and the plan already concedes the two merges will disagree. The stated use cases do not need it:
- *NAS plaintext mirror* is a one-way export. The server holds every head in plaintext; `serve --export-dir DIR` subscribing to the hub and writing heads with preserving writes is a few hundred lines: no chunking, no `decide` table, no merge, no index journal, no upload path, no retry scheduling. Read-only by construction, which is what a mirror wants.
- *Writable server folder* (`--vault-dir`, M8) is the real want, and in-process it is not the same problem: there is no network, no `stale` backoff, no catch-up cursor, no conditional write against a head you cannot see. Watch the directory, read the changed file, commit it; on commit, write the file. Merge happens once, locally, against a store you are already holding the lock on.
- *A headless two-way peer* already exists and is tested: `client/src/cli`. §2.7 deletes its publish step, which is what creates the need for the Go port. Un-deleting it costs a build config (§2.7 says so itself).

"Retained content, not agreement" (§2.6) is rule 10 being used to license a weaker property rather than to demand the right one. Two merge implementations produce conflict copies at different rates with different content, and every future merge fix lands twice in two languages forever.

**F2. Do not freeze-and-fork. Vertical slice first.**
Lanes A and B in parallel against a 200-line document assumes the hard parts are in the document. They are not: NFC edge cases, frame decode bounds, the empty-chunks/zero-size case, invite CRC placement, and `size == Σ chunks` interacting with folders are discovered in implementation. Lane B would spend a week against `fake-socket.ts` with no running counterparty. Sequence instead: M1a = hello + put + get + fetch + frames, plaintext, no invites, no admin surface; then start M2 against a real `serve`; finish M1b (invites, admin subcommands, backup/verify/purge) in parallel with M2. Add `protocol-fixtures.json` conformance as an executable both sides run, and a `jotrove conformance` subcommand the TypeScript suite can spawn.

**F3. Admin subcommands cannot revoke a live session.**
§2.3 has `invite`, `devices`, `revoke`, `mcp-token` writing SQLite directly while `serve` runs. Basalt's wire `revoke` closes the revoked device's live session (`TestRevokingClosesTheRevokedDevicesLiveSession`). A row deleted out of process does not: the running server keeps the authenticated session open and keeps fanning out every commit to a device you believe you revoked. Same for `mcp-token --revoke` against an in-flight streamable HTTP request. Fix: either a control channel (a unix socket in the data dir, or a SIGHUP that re-reads credentials), or the server polls a `credentials_generation` counter on every commit/fan-out, or admin subcommands refuse to run while `dirlock` shows a live server and tell you to use the wire op. State the chosen answer; do not leave revocation as a best-effort.

**F4. Move index maintenance out of the commit transaction.**
Two problems with §2.5:
- *Wrong failure direction.* An FTS5 insert that fails rolls back the commit, so a search-index bug fails a device's note write. Derived state must not be able to refuse a durable write.
- *Cost inside `commitMu`.* Indexing requires assembling the note, so every commit pays a full chunk-assembly. A 256-entry batch (protocol.md's limit) assembles 256 notes inside the commit lock. First upload of a whole vault will stall.
Design instead: durable `indexed_through_uid` cursor, an indexer goroutine walking `NextBatch` from that cursor, `index.fresh` computed as `indexed_through_uid == head`. `search_notes` reports staleness honestly, which mcp-tools.md already assumes. Rebuild-on-startup logic stays.

**F5. The size invariant needs a cheap form.**
`Σ chunks.Size(vaultID, name) == size` at commit is one lookup per chunk per entry, inside `commitMu`, with limits of 256 entries × 65,536 chunks. Carry the length in the chunks metadata row and sum in SQL in one statement per entry, or check only chunks uploaded in this session and trust names already verified at store time. Whichever, say so, because the naive form is a lock-held loop over the filesystem.

**F6. Backups are the real at-rest story, and the plan buries it.**
§3.6 says backups are plaintext and "encrypt them with the backup tool if they leave the box", in a parenthetical. That is the single largest practical regression from Basalt, where a stolen backup was useless. Make it load-bearing:
- `jotrove backup` refuses to write outside the data directory without `--plaintext-ok`, or grows `--encrypt-to <age recipient>`.
- `docs/server.md` states, as a requirement and not advice, that the data volume is on an encrypted filesystem (LUKS/FileVault/ZFS native).
- The restore rehearsal CI job (M9) covers the encrypted path, not just the plaintext one.
This is cheaper and more honest than adding application-level encryption, which cannot protect the SQLite metadata (paths are the most sensitive thing after content) with a pure-Go driver.

**F7. Promote the agent audit log and undo out of `ideas.md`.**
Both are marked "Do this early" in `plan/ideas.md` and then not scheduled. They are the reason it is acceptable to let a model write to your notes unattended:
- *Audit log* is five columns and an insert alongside the commit: `(uid, previous_uid, token_id, tool, path, at)`. Put it in M5, with `jotrove audit --since` and an MCP-writes section in the plugin's devices panel.
- *Undo* is "restore `previousUid` to its original path", which is `restore_note` with `to == path`. Put it in M5 as a plugin affordance and a CLI verb.
Without these, M10 moves a live vault to a system where an overnight agent run is unreviewable.

**F8. MCP token hardening.**
A static bearer that reads and writes the whole vault, forever, living in a config file on a laptop, is the highest-value secret in the system. Add to the `mcp_tokens` schema and to M4: `scope` (settle F-A2), `expires_at` with a default (90 days) and a rotation verb, per-token rate limiting (the plan has only a global 32-concurrent cap), and per-token path prefix scoping as an explicit later item rather than silence. Also: `last_used` updated "at most once a minute" means a stolen token used once may never show a `last_used` change at all; record `used_count` too.

**F9. §4.4 whole-file `write_note`: keep refusing, change the reason.**
Basalt's reason ("a matching base proves which bytes an edit starts from, not that the replacement preserved their meaning") is genuinely weakened by server-side history and a mandatory `base`: a whole-file write can no longer lose data. The reasons that survive the move are different and better: whole-file writes re-emit the note, which silently normalises frontmatter order, trailing whitespace and list markers the agent never meant to touch; and they produce a diff a human cannot review. Record *those*. Then add the tool agents actually reach for whole-file writes to get: `replace_section(path, base, heading, body)` on goldmark's AST: bounded, reviewable, and goldmark is already a dependency for links.

**F10. `badpath` must be visible, not logged.**
§4.1 refuses non-NFC paths at the server. macOS surfaces NFD from the filesystem; the plugin normalises, but a path that trips any §4.1 rule from any client becomes a file that silently never syncs. `refusedName` exists in `engine.ts`; the requirement is that a server `badpath` lands in the plugin's stranded/refused list with the path and the reason, and in `client status`. Add it to M2 as a task and to the M3 acceptance script.

**F11. Add a shell-level escape hatch in M1.**
`jotrove cat --path P [--uid N]` and `jotrove export --uid N --to FILE`. With plaintext storage this is twenty lines, and it is the property that makes the whole thing safe to trust: your notes are readable with the binary and nothing else. It is also what you will want at 2am. Missing entirely.

**F12. Purge: state the invariant, not just the flag.**
§4.5's `-keep-since 30d` is right. The invariant to write down and test is stronger and clearer: *the `previousUid` returned by any MCP write is readable for at least the retention window after that write*. Add `purge --dry-run`, and a test that purge with defaults never removes a `previousUid` named by an audit-log row inside the window.

**F13. Observability is absent.**
`/health` is inherited and nothing else exists. A server an agent writes to unattended needs `jotrove stats --json` extended with commits by author, index lag (`head - indexed_through_uid`), chunk store bytes, live session count, and the last N MCP calls. Add to M9.

**F14. No shadow period before M10.**
M10 moves the live vault the moment M5 and M9 land. §Scope refuses a second sync tool on the same local vault, so running both against the live vault is out. The honest version: pair Jotrove against a *copy* of the vault, run the agent against it daily for two weeks, and compare `verify -deep` output and note/byte counts against Basalt. Make that M9.5 with a written exit condition.

**F15. Write `docs/operations.md`.**
`llm.md` is installation. What is missing is the 2am document: how to tell whether a note is lost, how to read a path's history from the shell, how to extract a version without a client (F11), how to roll back an agent's overnight run (F7), what `badpath` in the logs means, and what to do when the index is behind.

### C. Small things
- `chunks.Store.Size(vaultID, name)` signature in the reuse map.
- Clock: MCP writes set `mtime = now` from server time while devices use local time, and conflict-copy names embed a timestamp. Say what happens when the server clock is wrong.
- §4.1 refuses any segment beginning with `.`, so a user's `.attachments` folder is permanently unsyncable. Correct, but document it rather than let it be discovered.
- The `mcp:` device-id prefix is refused at hello (good) but the prefix is user-visible in the devices panel; give those rows a display kind rather than leaking the id shape.
