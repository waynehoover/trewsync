# Syncidian (shangeethsivan/Syncidian)

Investigated 2026-09-22 at commit `db48414` (138 commits, created 2026-08-23, last push 2026-09-11, 0 stars, 1 fork). Citations of the form `syncidian:path:line` point into that checkout; `basalt:` and `PLAN.md §x` as in the brief.

## 1. Summary

- **What it is:** a Go server plus a single-file TypeScript Obsidian plugin that syncs a vault through a server-side working copy, commits that working copy with go-git and pushes it to one private GitHub repo per user, and exposes a hand-rolled JSON-RPC MCP endpoint whose writes go straight to GitHub through the Contents API. Multi-user, with a web dashboard, admin surface, waitlist and "agent-discoverability" endpoints.
- **Maturity:** three weeks old, written almost entirely by Cursor background agents (branch names `cursor/...`, PR bodies with `CURSOR_AGENT_PR_BODY`). About 5,000 lines of non-test Go, one 1,332-line `plugin/main.ts`. 131 Go test functions, none of which exercise a crash, a race, or a lost write.
- **License:** MIT, "Copyright (c) 2026 Shangeeth Sivan" (`syncidian:LICENSE`). Copying is legally fine with attribution.
- **Stack:** Go 1.22, `modernc.org/sqlite` (WAL, `SetMaxOpenConns(1)`), `github.com/go-git/go-git/v5` v5.12.0, `nhooyr.io/websocket`; plugin uses `requestUrl` for HTTP and a browser `WebSocket` for live events.
- **Verdict:** almost nothing worth reusing as code, but it is the single most useful cautionary tale we have for "Git as the history backend". Every durability rule in PLAN §8 is violated somewhere, and the project's own PR history (#38, #39, #48, #51, #59, #60) documents, step by step, how making GitHub the source of truth with two writers led to hard resets and deletion-by-absence on every device.

## 2. Architecture in brief

**Server state.** Per user: a plain directory `data/vaults/<userId>/` that is simultaneously the sync working copy and a git worktree (`.git` inside it), plus SQLite `data/syncidian.db`. The `files` table is one row per `(user_id, path)` with `hash, size, mtime, deleted` and nothing else (`syncidian:internal/store/migrations.go:208`). There is **no version history on the server**: history exists only as git commits, and only if the commit and push succeeded.

**Sync protocol** (HTTP, JSON, base64 bodies, `syncidian:internal/server/sync.go`):
- `POST /api/v1/sync/plan` sends every local path with `hash` and `base_hash` (the client's last-known server hash, kept in the plugin's `data.json` as a `hashes` map). `PlanSync` does a three-hash comparison and returns `Pull / Push / Delete / Conflicts` (`syncidian:internal/syncengine/plan.go:60`).
- `GET /api/v1/sync/file?path=` returns base64 content, falling back to a GitHub Contents API fetch when the working-copy read fails (`sync.go:209`).
- `POST /api/v1/sync/push` carries up to 40 files (6 on mobile, `syncidian:plugin/mobile.ts:42`) with content, `base_hash`, and optional `renamed_from`. `ClassifyPush` decides accept, noop or conflict; a conflict first goes through `AutoMerge`; the file is written with `os.WriteFile`; then the request synchronously runs `commitAndMaybePush` (`sync.go:331`, `:721`).
- Live updates: a WebSocket hub per user broadcasting `file_changed` (optionally with the body inline, up to 256 KiB, `syncidian:internal/server/server.go:58`) and `github_synced`. Clients whose socket fails poll `GET /api/v1/sync/manifest` every 15 s, and every client polls on focus, visibility, `online`, and Capacitor `resume`.

**Git mapping.** One commit per push HTTP request, made by `git add -A` over the whole worktree (`syncidian:internal/gitx/repo.go:62`, `:102`), all with the same configured author, messages `Syncidian: vault update` / `move` / `delete` / `resolve conflict <path>`. The client debounces 3 s after the last edit (`syncidian:plugin/main.ts:54`), so a writing session produces a commit at every pause. Push to `origin main` happens in the same request under a per-user mutex; a push failure is reported as `git_error` in the response but the write is already accepted. Only `main` is supported.

**MCP.** `POST /mcp`, JSON-RPC, protocol `2024-11-05`, no SDK, no sessions, no SSE (`syncidian:internal/mcp/mcp.go`). Auth is the same `sk_sync_` bearer as the plugin, or the dashboard session cookie, or a username/password exchange at `POST /api/v1/mcp/login`. Every MCP read and write goes to GitHub through the Contents API (`syncidian:internal/server/mcp_notes.go`), explicitly *not* the server working copy (PR #39). Writes then broadcast `file_changed` with the body to live devices.

**Reconciliation with GitHub** (the part that matters). Because MCP commits land on GitHub without touching the server's local repo, the two histories diverge. The fix (PRs #48, #51, #59, #60) is that every plugin `fullSync`:
1. fetches GitHub's recursive tree and **deletes every local file not in it** (`syncidian:plugin/main.ts:349`, `:495`);
2. calls `POST /api/v1/github/sync`, which **hard-resets the server worktree to `origin/main`, deletes untracked files, and tombstones every SQLite row missing from GitHub** (`syncidian:internal/server/github.go:159`, `syncidian:internal/gitx/repo.go:130`, `:178`);
3. deletes local files again against the returned list, then runs the ordinary plan, skipping pulls and pushes for paths not on GitHub (`main.ts:387-398`).

**Conflicts.** Stored as two blobs in a `conflicts` row; the plugin shows a three-textarea modal (this device, server, merged); `POST /api/v1/conflicts/{id}/resolve` writes the chosen bytes (`sync.go:667`).

**Secrets at rest.** GitHub App PEM, OAuth client secret and installation tokens are AES-256-GCM sealed with a key from `SYNCIDIAN_DATA_KEY` or an auto-generated `secret.key` in the data directory (`syncidian:internal/store/crypt.go`). Notes, conflict blobs, and the git history are plaintext.

## 4. Ideas worth adopting

1. **Foreground resync must not trust an `OPEN` socket.** Their comment at `syncidian:plugin/main.ts:980-985` and `docs/architecture.md` §4: Electron and mobile WebViews freeze timers and sockets in the background, and a socket can come back reporting `OPEN` having delivered nothing. They poll the manifest on every foreground even when the socket looks healthy. Basalt already watches `visibilitychange`, `focus` and `online` (`basalt:client/src/plugin/resume.ts:3`); Syncidian additionally listens for the Capacitor/Cordova `document "resume"` event (`main.ts:154`). **Lands in:** M2 plugin task list, as a check that the resume path forces a catch-up exchange (not just a reconnect-if-closed), and as an unverified candidate signal to test on Android. I have not confirmed Obsidian mobile dispatches `resume` on `document`; test before adding it.
2. **Record MCP `clientInfo` per token.** They store the `initialize` `clientInfo.name/version` and User-Agent per token and count calls per tool (`syncidian:internal/mcp/mcp.go:125-159`, `migrations.go:290`). Cheap, and it answers "which client used this token" in the audit log. **Lands in:** PLAN §3.3 `operations` (add `client_name`, `client_version` columns, bounded and normalised like any untrusted string) and M5 task 2.
3. **Append under a heading.** `append_to_note` with an optional `heading` inserts before the next heading of the same or higher level (`syncidian:internal/mcp/organize.go:283-374`). This is the most common agent write on daily notes ("add to ## Log"). Their implementation trims the note's trailing whitespace and re-reads the base at write time, so do not port it, but the tool shape is right. **Lands in:** `plan/mcp-tools.md`, as an optional `heading` on `append_note` with exact semantics (heading matched by exact line, ATX only, fails with `no_match`/`ambiguous_edit` when missing or duplicated, never creates a heading silently), or as the first form of `replace_section` in `plan/ideas.md`.
4. **Deploy guards against two processes on one volume.** `railway.json` sets `overlapSeconds: 0` and `requiredMountPath: /data` so a rolling deploy cannot run two replicas against one SQLite, and a deploy without a volume fails instead of starting empty (`syncidian:railway.json`). We already take an exclusive server lock (`basalt:server/cmd/basaltd/main.go:305`); the lesson is to document that a PaaS rolling deploy will make the second instance fail its health check on that lock, and to refuse to start on an empty store in a directory that looks ephemeral. **Lands in:** M9 docs and the M5.5 `doctor` checks.
5. **A one-way Git export is worth doing, for the reasons their design shows and in the opposite shape.** See §7 item 1 and §8.

Explicitly **not** adopted: the discovery endpoints. `/auth.md`, `/.well-known/mcp/server-card.json`, `api-catalog`, `ai-catalog.json`, `agent-skills` index, markdown `GET /` and an AI-bot `robots.txt` with `Content-Signal: ai-train=yes` (`syncidian:internal/server/agents.go`) are aimed at agent-readiness scanners for a public SaaS landing page. For a single-user server behind Tailscale they only enumerate the service and its version to anyone who can reach the port. Worse, they publish `oauth-protected-resource` and authorization-server metadata that is not OAuth at all (`agents.go:197-227`: the "token endpoint" is a password exchange, `grant_types_supported: ["password"]`, the "authorization endpoint" is GitHub sign-in). An MCP client that follows the spec's discovery path after a 401 will find that document and try a flow that cannot work. If Trew ever wants discovery, a static server card behind the same auth is the most it needs, and it must not advertise OAuth it does not implement (PLAN §2.3 refuses OAuth).

## 5. Gotchas and platform quirks they discovered

1. **Obsidian's vault index lags the filesystem.** `getAbstractFileByPath` returns null for files and folders already on disk (at startup, or created behind the vault's back), so `createFolder`/`createBinary` throw "already exists". They check `adapter.exists` first and fall back to `adapter.writeBinary` (`syncidian:plugin/main.ts:568-617`, PR #23 "Fix Obsidian sync failing with Folder already exists"). Basalt's preserving adapter already handles this class; keep the regression case.
2. **Sleeping sockets report `OPEN`.** See §4 item 1 (`main.ts:980`, issue #40, PR #42).
3. **`requestUrl` versus `fetch` on mobile.** They moved all HTTP to `requestUrl` because `fetch` in the Android/iOS WebView hits CORS and mixed-content blocks (`main.ts:231`). Irrelevant to our WebSocket protocol, relevant to any future HTTP side channel from the plugin (history viewer, health probe).
4. **`localhost` on a phone is the phone,** and iOS blocks plain `http://` (`main.ts:272-302`). They refuse loopback URLs on mobile with a specific message. Cheap, worth copying as a plugin settings validation in M2.
5. **`getFiles()` versus `getAllLoadedFiles()`.** Their comment at `main.ts:418` says `getAllLoadedFiles()` can miss vault files on mobile. Unverified by me; Basalt should already use the complete listing, confirm in M2.
6. **GitHub's recursive tree API truncates** (100,000 entries or about 7 MB) and their `ListFiles` ignores `truncated` (`syncidian:internal/githubapp/contents.go:116-140`). Their own audit (issue #64) called this "mass vault deletion" and it is still unfixed at HEAD, because the truncated list is the deletion authority in §2's reconciliation.
7. **The Contents API is not a file store.** One API call per file read (search reads every note, one request each, `syncidian:internal/mcp/mcp.go:533-583`), one commit per file write (a 200-file `bulk_move` is 400 commits, `organize.go:484`), bodies over 1 MB come back without content, and installation tokens are rate-limited per hour. `http.DefaultClient` has no timeout (`syncidian:internal/githubapp/client.go:368`), and `importGitHubVault` calls it while holding the per-user git mutex (`github.go:169-173`).
8. **Git does not record renames.** PR #27 and the README claim a move is sent "as a Git rename, not a delete followed by an add" (`README.md:631`, `docs/architecture.md` §6). Git stores trees only; rename is inferred at diff time by similarity. Any export we build needs no rename machinery, and nobody should design around this misconception.
9. **Syncing `.obsidian/` sends other plugins' secrets to GitHub forever.** Their ignore list excludes only workspace files and their own plugin folder (`syncidian:internal/syncengine/plan.go:6-32`), so every other plugin's `data.json` (API keys for AI plugins are common) is committed to the user's repository history. Our §4.1 refusal of dot segments avoids this; any Git export must keep the same exclusion and say so.
10. **Obsidian community review lint** flags `@typescript-eslint/no-unsafe-*` across the plugin (issue #57), and BRAT needs a release whose tag equals `manifest.json` version with the three files attached as assets (README "Publishing"). Useful checklist items for M9.

## 6. Their bugs or weaknesses we must not repeat

Each is checked against their code at HEAD; the first two were reproduced.

1. **Two-way "merge" that silently discards edits.** `AutoMerge(local, remote)` has no base. After stripping the common prefix and suffix, if the unchanged part is at least as large as the changed middle, it returns `local` whole (`syncidian:internal/syncengine/merge.go:46`). I ran it: a 20-line note with the laptop editing line 3 and the phone editing line 12 returns `ok=true` with the laptop's edit and **without the phone's**. A local deletion at the end is also undone (`AutoMerge("keep\n", "keep\nsecret I deleted\n")` returns the remote). The tests assert "the pusher wins" (`merge_test.go:16`). This runs on every conflict before the modal (`sync.go:394`). Rule 5 and rule 10. Basalt's three-way merge with validity gates (`basalt:client/src/core/merge.ts`) is the reason we keep one engine (§2.6).
2. **The CAS on GitHub is defeated by re-reading the base at write time.** MCP edits read the note, compute new bytes, then `Put` does a fresh `GetFile` to get the blob SHA and writes with that SHA (`syncidian:internal/server/mcp_notes.go:46-70`). A concurrent change between the read and the put is overwritten, because the precondition is taken from the current version, not from the version the edit was computed on. Same shape for `update_note` (blind overwrite, no base parameter at all, `mcp.go:593`). PLAN's `base` UID carried from the read (§2.4, `plan/mcp-tools.md`) is exactly the fix; keep it mandatory.
3. **Two writers to the source of truth, reconciled by hard reset.** Devices write the server worktree and `git push`; MCP writes GitHub directly. When a device push was accepted and committed locally but the push to GitHub failed (token expiry, network, non-fast-forward after an MCP commit), the next `fullSync` from any device runs `ResetToRemote`, which hard-resets and purges untracked files (`repo.go:166-169`), then tombstones every row not on GitHub (`github.go:213-277`). The accepted write is gone from the server, and the device that made it pulls GitHub's older content over its own on the next plan (client hash equals base, server differs, so Pull). Acknowledged-then-discarded: rule 1 and rule 3.
4. **Deletion by absence, on every device, every sync.** `dropLocalNotInRemote` deletes any local file not in GitHub's tree before the plan runs (`main.ts:349-359`, `:495-504`), and recursively `rmdir`s folders whose paths are not tree prefixes (`main.ts:517-543`). A note created offline, or pushed to the server but not yet to GitHub, is deleted locally. A truncated or failed tree listing (§5.6) is treated as complete. Rules 2, 3 and 6 at once: a failed read becomes an empty result, a delete happens with no verified copy, and deletions are inferred from absence rather than recorded as entries.
5. **The pending queue is discarded.** `fullSync` starts with `this.pending.clear()` (`main.ts:344`), and `queueChange`/`queueRename` ignore events while `syncing` or `applyingRemote` is non-zero (`main.ts:784`, `:805`). Edits made during a sync, or to any file while any remote write is being applied, are never queued; they surface only if a later full sync happens to hash the file, and `pollRemote` only triggers a full sync when the *server* manifest differs (`main.ts:1017-1046`).
6. **Live events overwrite unsynced local edits.** A `file_changed` with content is written straight over the local file with no base check (`main.ts:953-958`). If the user typed in the last 3 s (still in the debounce), their edit is overwritten, the resulting `modify` event is suppressed by `applyingRemote`, and the pending flush then pushes the remote bytes back as if they were local.
7. **Broadcasts are unordered.** `Hub.Broadcast` spawns one goroutine per client per message (`syncidian:internal/server/ws.go:53-71`), so two quick changes to one path can arrive in either order. A device that applies the older one records its hash and, with the socket up, never polls; it stays stale until the next foreground. Basalt's ordered per-session delivery with covered ranges (protocol rule 3) is what prevents this.
8. **No transaction, no lock, no fsync on the write path.** `classifyPushFile` then `applyFile` read and write with no lock spanning them (two concurrent pushes to one path both pass classification), `os.WriteFile` is not atomic and not fsynced, and the SQLite row is updated after the file in a separate statement (`sync.go:458-497`). The git mutex covers only commit, push and reset, so a push that writes a file while `importGitHubVault` is purging can have its file deleted underneath it.
9. **Moves overwrite the destination.** `applyMove` does `os.RemoveAll(toFull)` if the destination exists, and checks the source's base but never the destination's (`sync.go:521-523`). Conflict resolution writes the chosen bytes with no check that the server head is still what the conflict recorded (`sync.go:695`). Deletes with an empty `base_hash` are accepted unconditionally (`sync.go:384-389`).
10. **A 32 MiB JSON body cap on base64 batches** (`server.go:362`). A batch over the cap fails as "invalid json"; because the pending map was already swapped out (`main.ts:875-876`), the whole batch drops out of the queue.
11. **MCP writes can plant plugin code on every device.** `vaultRel` rejects only `..` and the ignore list (`syncidian:internal/mcp/path.go:11-29`); `.obsidian/` is writable. `move_note` accepts any destination extension (`organize.go:393-405`). An agent with modify permission (or a prompt-injected one) can `create_note a.md` then `move_note` it to `.obsidian/plugins/x/main.js`, plus `manifest.json` and `community-plugins.json`, and the sync delivers it to every device. PLAN §4.1's dot-segment refusal closes this; add this chain to the M5 injection fixtures as a named case.
12. **MCP permissions are per user, not per token, and the MCP token is the sync token.** One `sk_sync_` value both syncs arbitrary files and calls MCP with whatever the user enabled (`syncidian:internal/server/server.go:302-321`, `mcp.go:169`). A password exchange mints a new long-lived token with no expiry (`auth.go:492`). PLAN §2.3's separate MCP tokens with scope, expiry and `used_count` are right.
13. **Protocol-level MCP mistakes.** Tool failures are returned as JSON-RPC errors rather than `isError` results (`mcp.go:70-73`), so many clients show a transport error instead of letting the model read it; `notifications/initialized` gets a response body although it is a notification (`mcp.go:112`); the server card claims `streamable-http` with no session, SSE or `Accept` handling. Results are bare text with no untrusted-content separation, and reads are unbounded apart from GitHub's own 1 MB limit.
14. **Clock and unit drift.** Device pushes record `mtime` in seconds, MCP writes in milliseconds into the same column (`mcp.go:604`, `organize.go:436`).
15. **Cross-site WebSocket.** `websocket.Accept` with `InsecureSkipVerify: true` and `OriginPatterns: ["*"]`, falling back to the session cookie (`ws.go:108-131`). `SameSite=Lax` blocks most cross-site cases; same-site origins get note bodies. We send the token in-band in `hello`, so keep refusing cookie auth on the socket.

## 7. Where they contradict our plan, and who is right

1. **Git (on GitHub) as the source of truth, versus our store as the source of truth.** They are wrong, and their history shows why without argument from us. Making an external, network-reached, eventually-consistent system authoritative forced three things: reads over the network per call, reconciliation of two writers by reset, and deletion by absence. Each "fix" (PRs #48, #51, #59, #60) made reconciliation more destructive. Git's model has no conditional write on a path, no notion of a device's base, and no record of a deletion other than absence from the next tree, which is exactly the property rule 6 forbids. Our store has all three. **But Git as a one-way export is a good idea** for Trew, for reasons they correctly sensed: an offsite, standard-format, tool-friendly history (`git log -p`, blame, any host) that survives a bug in our own format is a "verified copy elsewhere" in the sense of rule 3, and it is the best answer to lock-in anyone could ask for. The shape that works is the inverse of theirs: derived from the store after commit, never read back, never able to delay or refuse a device write, resumable from a durable watermark, and with push failure affecting only the export's own status. Details in §8.
2. **A server-side working copy plus `git add -A`, versus content-addressed chunks and a version log.** Ours is right. Their working copy means every write is a filesystem write with no atomicity, every commit rescans the whole tree, history exists only when a commit succeeded, and a reset can destroy accepted writes. If we build an export, build git trees from store heads directly (blob objects from assembled bytes, trees in memory), with no worktree on disk at all.
3. **One commit per device push request, versus our per-entry versions.** For an export, neither extreme is right: per-request commits are noise (a commit at every 3 s typing pause), per-file Contents API commits are worse (400 for one bulk move). Coalesce device versions into one commit per quiet window, and give each MCP `CommitOperation` its own commit so an agent's change is one reviewable diff that names its `opId`.
4. **Hand-rolled MCP without an SDK.** PLAN M4 task 1 asks to evaluate hand-rolling. Syncidian is evidence of what a careless hand-roll gets wrong (notifications answered, errors at the wrong layer, claimed transport not implemented). That does not decide the question, since `hister`'s hand-roll is careful, but it sharpens it: if we hand-roll, the M4 tests must cover notification handling, `isError` results, and `Accept`/202 behaviour for streamable HTTP explicitly.
5. **Multi-user, admin surface, hosted service.** They took it on from day one and spent a large share of the commits on landing pages, waitlists, six-tap reveals and GitHub App plumbing while the sync lost data. Our one-person scope (PLAN §1 "Scope and refusals") is right.
6. **Reversible secrets in SQLite.** They need them because the server holds GitHub App keys. We store only hashes (device, invite, MCP tokens), which is strictly better. The first time Trew needs a reversible secret (a Git export push credential, a webhook signing key), keep it out of SQLite: a path to a 0600 file named in config, read at start, and fail closed if unreadable. Do not build a field-sealing layer whose key lives in the same data directory.

## 8. Concrete recommended changes to PLAN.md

- **`plan/ideas.md`, "A milestone of work, high payoff": add "Git history export"** beside `serve --export-dir`, with this specification so nobody rebuilds Syncidian:
  - One-way: `serve --git-export DIR` maintains a **bare** repository under the data directory (or a path given). It is derived state, maintained like the search index (PLAN §2.5): a durable `git_export_state (exported_through_uid, commit_sha, branch, epoch)` row, an asynchronous worker, never inside `commitMu`, never able to refuse or delay a device write.
  - Never read back. No import, no pull, no reset, no reconciliation. If the repository is changed externally, the exporter refuses and reports it; it does not "fix" either side.
  - Trees built from store heads with go-git object writes (Apache-2.0), no worktree. Deleted paths are simply absent from the next tree; renames need nothing (Git infers them).
  - Commit granularity: one commit per MCP operation, message and trailers carrying `opId`, tool and actor label; device versions coalesced per quiet window (for example 5 minutes or N versions), author set to the device label, committer time from `operations.committed_at` or the server clock, never client `mtime`.
  - Exclusions stated beside the flag: dot-segment paths are already unsyncable (§4.1); attachments over a size threshold are excluded by default because Git history cannot shrink; conflict copies are included.
  - Pushing is the user's business in v1 (their own cron `git push` from the bare repo, or `git clone` over SSH). If Trew ever pushes, the credential is a 0600 file path, push failure only sets export status, and `doctor` reports export lag.
  - Stated plainly in the Privacy section: exported history is plaintext, cannot be purged by `trew purge` (§4.5), and whoever hosts the remote reads every note and every deleted version.
  - Acceptance: an export rebuilt from scratch equals the incremental export byte for byte; SIGKILL during export resumes without a duplicate or missing commit; `git checkout` of the export tip matches the witness-device inventory used in M10.
- **PLAN §4.1:** add one sentence recording why dot segments stay refused even for MCP: "an agent that can write `.obsidian/plugins/*/main.js` can execute code on every device", with Syncidian's `create_note` plus `move_note` chain (`syncidian:internal/mcp/organize.go:393`) as the M5 injection fixture.
- **PLAN §2.4 / `plan/mcp-tools.md` "Mutation tools":** state that `base` must be the UID the edit was computed from, supplied by the caller, and that the server never substitutes the current head. Cite Syncidian's re-read-SHA lost update (`mcp_notes.go:52-69`) as the failure this rule prevents.
- **`plan/mcp-tools.md` `append_note` / `prepend_note`:** add an optional `heading` (exact ATX heading line, insert before the next heading of the same or higher level, `no_match` if absent, `ambiguous_edit` if duplicated, no whitespace normalisation of the rest of the note), or record it as the first form of `replace_section` in ideas.
- **PLAN §3.3 `operations`:** add `client_name` and `client_version` from MCP `initialize`, normalised and length-capped as untrusted input (§4.10).
- **PLAN M4 task 1:** if hand-rolling, the test list must include: notifications receive no response body (202 for streamable HTTP), tool failures are `isError` results not JSON-RPC errors, unsupported `Accept` or methods answer as the spec says.
- **PLAN M2 (plugin):** add acceptance cases taken from Syncidian's bugs: an edit typed during a sync is queued and pushed; an edit typed within the debounce window survives an incoming remote version of the same file (becomes a merge or conflict copy, never an overwrite); the foreground handler forces a catch-up exchange even when the socket reports `OPEN`; mobile settings refuse loopback URLs with a clear message.
