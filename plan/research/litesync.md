# LiteSync (KJoner/litesync + KJoner/litesync-server)

Investigated 2026-09-22. Plugin `KJoner/litesync` at `cae9748` (0.19.0, 59 commits, 2026-08-08 to 2026-08-30). Server `KJoner/litesync-server` at `08629b8` (v0.19.0-rc.3, 48 commits since the repo split on 2026-08-09). Both cloned under the session scratchpad. Neither repo has a single GitHub issue or PR, and the plugin has 2 stars: all evidence below is code, commit messages, the `docs/releases/` notes, READMEs and `AGENTS.md`. The design docs the code cites (`docs/开发计划/`, ADR-001 to ADR-010) are gitignored and not published. Citations: `litesync:` is the plugin repo, `litesync-server:` the server repo. Two claims were checked by running code, not by reading it: the merge-base loss in §6.1 (a Go test against their server) and the merge behaviour in §6.3 (their merge module run under `tsx`). Their full server suite passes (`go test ./...`, about 95 s).

## 1. Summary

- **What:** an Obsidian plugin plus a Go server for self-hosted sync with optional end-to-end encryption, per-file version history, automatic three-way merge with a resolver UI, encrypted note sharing, a read-only web reader, restic backup to R2, and since 0.18 invite-only multi-user and multiple vaults per user. The server treats content as opaque bytes.
- **Maturity:** three weeks of very fast, entirely AI-generated work (every commit and `AGENTS.md` §10 name `Co-Authored-By: Claude Fable 5`). It was field-tested by the author on Windows, iOS and the web in numbered acceptance rounds (T2.3, T3.5, and so on), and those rounds produced the most valuable material here. Engineering vocabulary is strong (failpoints, invariants INV-01 to INV-12, crash points, an auth matrix generated from the route table), but several claims do not match the code (§6.6).
- **License:** plugin **MIT** (`litesync:LICENSE`, "Copyright (c) 2026 KJoner"): reusable with attribution. Server **AGPL-3.0** (`litesync-server:LICENSE`, relicensed in `litesync-server:72ae169`), and that includes the web reader and pairing landing page in `litesync-server:web/`: **ideas only, never copy**.
- **Stack:** plugin TypeScript, esbuild, own Myers diff and diff3, Web Crypto, `requestUrl`, minAppVersion 1.13.0 (for `app.secretStorage`). Server Go, `modernc.org/sqlite` with one connection, net/http REST (no WebSocket; clients poll `/changes?since=N`), whole-file content-addressed blobs, restic forked for backup.
- **Verdict:** little code worth taking. Its merge is looser than Basalt's in ways that silently combine edits (§6.3), and its history retention loses merge bases within minutes (§6.1), which is independent confirmation of PLAN §4.5 from a real system. High value as evidence: a measured iOS and Android filesystem matrix, iOS WebKit form quirks, an Obsidian rename-emits-modify quirk, a server-side case-fold collision rule we lack, a production deadlock that `/health` hid, and several good server hygiene ideas (two-round GC, quarantine, ack-gated tombstone purge).

## 2. Architecture in brief

**Server storage.** `/data/sync.db` plus `/data/blobs/` (`litesync-server:README.md:22-31`). Identity is a server-issued `file_id`; `path` ("pseudonym") is a mutable attribute. Tables: `file_objects`, `file_heads` (one row per live object, unique on `(vault_id, pseudonym)` and on a case-folded canonical key), `tombstones` (a separate ledger, never dropped by default), `object_versions` (one row per upload, with `action` of upsert, merge, restore or delete, `device_id`, `operation_id`), `object_changes` (the sequence feed), `devices` with `last_acked_sequence` (`litesync-server:internal/db/schema.go:36-160`). Blobs are whole files, named `HMAC(vaultSecret, sha256(content))` since 0.16 so dedupe is per vault. No chunking: a 100 MB attachment edit uploads 100 MB and stores another 100 MB version.

**Write path.** `PUT /api/v1/file` with the path, `X-Base-Revision`, `X-Content-Hash`, and an operation id in headers. The body is streamed to a temp file and hashed outside the lock (`litesync-server:internal/sync/service.go:452`), then under one global mutex (`:466`): repo-state guards, idempotency (content equals head, `:516`; same operation id, `:525`), tombstone and case-fold collision checks (`:558-575`), base check, blob rename into place with directory fsync, then one SQLite transaction for head, change, version, and **inline history pruning** (`:652-667`). `synchronous=FULL` by default. `SetMaxOpenConns(1)` (`litesync-server:internal/db/db.go:29`).

**Read path and transport.** Plain HTTP. `GET /changes?since=N` returns the feed, or `resyncRequired` once the feed has been trimmed (90 days or 100,000 rows), after which the client reconciles against `GET /snapshot`. No push channel: the plugin polls every 30 s (60 s minimum on mobile), syncs 3 s after a local edit, and 2.5 s after returning to the foreground (`litesync:src/main.ts:49-53,505-514,584-588`).

**Plugin engine.** Event-driven queue plus a scan. Vault `create`/`modify`/`delete`/`rename` events enqueue operations that are persisted before they count as accepted (`litesync:src/sync/queue.ts:1-16`, `litesync:src/main.ts:826-872`); each round is pull, scan (mtime and size against a cached `FileState`, `litesync:src/sync/push.ts:49-80`), push, pull. All remote writes go through one `LocalCommitter` that writes a staging file in the plugin directory, re-hashes the target, moves the old file to `recovery/`, and renames staging into place (`litesync:src/sync/local-commit.ts:167-269`). State is one JSON document written to alternating A/B slots with a checksum and a per-write ownership token (`litesync:src/state/store.ts:433-470`).

**Conflicts.** Both sides changed a `.md`: fetch the base from server history by the tracked revision, run a layered merge (frontmatter by key, sections, line diff3, list-item union, token diff3), upload a clean result, otherwise record a "pending conflict" that freezes that path in both directions until someone opens the resolver (`litesync:src/sync/auto-merge.ts`, `litesync:src/sync/pull.ts:892-893`, `litesync:src/sync/push.ts:384,661`). Anything else, or a missing base, keeps both versions as a conflict copy (`litesync:src/sync/conflict.ts:14-89`).

**Everything else.** E2EE envelopes LSE1 to LSE4, encrypted path pseudonyms, device-signed checkpoints, size and timing obfuscation, share links with the key in the URL fragment, web reader, restic backup, multi-tenant `VaultScope`. Out of scope for Trew and not reviewed in depth.

## 4. Ideas worth adopting

1. **Refuse case-fold collisions on the server** (PLAN §4.1, protocol.md "Paths"). They keep a canonical key `lower(NFC(path))` and a unique index on it (`litesync-server:internal/storage/canonical.go:13-15`, `internal/db/schema.go:133`), and refuse a new path that folds onto a live one with `422 CANONICAL_COLLISION` (`internal/sync/service.go:571-575`). Basalt folds client side (`basalt:client/src/core/paths.ts:145`), but Trew adds a writer with no filesystem at all: an MCP `create_note("note.md")` beside `Note.md` would be accepted by the server and then collide on every macOS and Android device. The server is the only place that sees every writer, so the rule belongs there too. Pin the fold in `protocol-fixtures.json`, because Go and JS disagree (§5.6).
2. **Pin merge bases by device progress, not by age or count** (PLAN §4.5). LiteSync loses bases (§6.1), yet it already has the mechanism that would fix it and uses it only for tombstones: a tombstone is purged only when older than its retention and at or below the minimum `last_acked_sequence` of non-revoked devices (`litesync-server:internal/sync/restore.go:244-274`). Apply the same rule to history: a version stays while any non-revoked device's applied checkpoint is at or before the point where it was displaced, because that device may still need it as its merge base. PLAN already has applied-checkpoint receipts (PLAN §1, §4.8).
3. **Orphan GC in two persisted rounds with an age gate** (PLAN §4.5 purge, M5.5). A blob must be unreferenced in two consecutive maintenance rounds, the candidacy count is stored in SQLite so a restart does not reset it, the final check is made under the write lock, files younger than an hour are skipped to cover "body written, transaction not committed", and GC is skipped entirely while a backup, scrub or migration runs (`litesync-server:internal/sync/maintenance.go:295-388`). Our chunk store has exactly the same window between `chunks.Writer.Close()` and the entry commit (PLAN §4.3 step 3).
4. **Quarantine, and a typed error instead of 404** (PLAN §8 rule 2, M5.5 doctor). A blob whose bytes fail verification is moved to `blobs/_quarantine/` and kept for forensics, and reads return `503 CONTENT_CORRUPTED` rather than `404` (`litesync-server:README.md:688-692`, `internal/storage/blobs.go:253-290`). A missing or corrupt chunk must never read as "the note is gone".
5. **Backup staging as `VACUUM INTO` plus hard-linked blobs, taken under a brief write lock, with a manifest carrying the latest sequence**, and **restore refusing to run without rotating the epoch** (`litesync-server:README.md:575-593,685-688`). PLAN already mints a new epoch on restore (PLAN §5 M1 item 8); the hard-link staging and the manifest are the parts to take into Basalt's `backup.go` rework (PLAN M1 item 12).
6. **Client version and platform in every hello, stored per device** (protocol.md handshake, M5.5 doctor). They send `X-Client-Version` on every request so `obsync migration preflight` can answer "has every device upgraded?" before an irreversible step (`litesync:docs/releases/0.17.0-rc.1.md`). Trew will bump protocols; `doctor` and `devices` should show each device's client version and refuse or warn before a server change that old clients cannot follow. Their ops page also keeps revoked devices listed, because "when was it last active" is the question you ask about a stolen phone.
7. **An authorization matrix generated from the route table** (M4 and M5 tests). Their test scans `router.go`, so a new route is covered automatically and a public route must be registered as public on purpose (`litesync-server:README.md:238-240`, `internal/api/tenancy_matrix_test.go`). The Trew equivalent is generated from the MCP tool registry and the control-socket command table: every tool against no token, expired token, revoked token, read scope and write scope. This is the enforcement half of PLAN §2.3's "enforced three times".
8. **QR through an HTTPS landing page, secret in the fragment** (PLAN §2.3, M9). Their QR encodes `https://server/p/<id>#secret=...`; any camera app opens a browser, a static page builds the `obsidian://` link locally, and the fragment never reaches the server or a proxy log (`litesync-server:internal/api/pairing.go:66-76`). Some Android camera apps do not open custom schemes from a QR code, and PLAN's `obsidian://lyell?invite=` puts a live invite token in whatever handles that URL. Trade-off: it needs one unauthenticated static page on the server. Worth deciding on purpose.
9. **Blocking notices on mobile** (PLAN §4.9). "Mobile has no status bar, an 8-second notice is a notice nobody sees" (`litesync:src/sync/context.ts:66`), and a revoked device used to back off forever in silence (`litesync:docs/releases/0.17.0-rc.4.md`, T5.2). Credential refusal and stranded paths need a persistent notice that stays until dismissed or resolved, and the revoked device must stop retrying.
10. **Stale resurrection check** (compare Basalt). A tombstone carries `prior_content_hash`, so an upload at a deleted path whose bytes equal the pre-delete content is recognised as an old copy coming back rather than a new note (`litesync:src/sync/push.ts:640-660`). Confirm that Basalt's deletion entries give the engine the same distinction; if not, it is a small field on the deletion entry.
11. **Device credential in `app.secretStorage`** (reuse-map plugin persistence). They keep the token out of `data.json` entirely (`litesync:src/main.ts:754-812`). PLAN puts `deviceToken` in `data.json`, so any tool that copies `.obsidian` (Obsidian Sync's plugin-settings option, iCloud, a dotfile backup) clones the device identity onto a second device, which then shares one applied cursor. The cost is a minAppVersion bump from Basalt's 1.7.2 (`basalt:manifest.json:5`) to whatever version introduced `secretStorage` (LiteSync pins 1.13.0); verify before deciding. The weaker alternative is to detect a clone, as their ownership token does for state files.

## 5. Gotchas and platform quirks they discovered

1. **iOS and Android disagree about names in opposite directions.** Measured on real devices with their probe: iOS is case-sensitive and normalises Unicode; Android is case-insensitive and does not normalise (`litesync:README.md` "Platform limitations", `litesync:docs/releases/0.17.0-rc.2.md`). A rule chosen per local platform makes two devices disagree about whether two names collide, then overwrite each other. Only the strictest rule across platforms is safe, which is what Basalt's `foldPath` already does (`basalt:client/src/core/paths.ts:127-151`). For Trew the relevant pair is a Linux desktop (case-sensitive) and an Android phone (not).
2. **Every platform they measured supports rename into an empty slot**, including iOS and Android (`litesync:docs/releases/0.17.0-rc.2.md`). Their probe tests "rename to a path that does not exist" rather than "rename over an existing file", because Windows refuses the second and a probe of the wrong operation marked every Windows user non-atomic (`litesync:src/sync/local-commit.ts:271-318`). Relevant to any Basalt code that assumes rename-over-existing on mobile.
3. **Renaming a note that is open in the editor also fires `modify`** (`litesync:docs/releases/0.17.0-rc.4.md`, T3.2/T3.5). In their path-keyed queue the modify overwrote the queued move with a plain upsert, the new path was uploaded as a new object, and history restarted from revision 1. Fix: an upsert never overwrites a queued move for the same path (`litesync:src/sync/queue.ts:126-137`). Basalt's engine is scan-driven, but a plugin lifecycle test for "rename an open note, then keep typing" belongs in M2.
4. **iOS WebKit treats any text field plus password field in one document as a login form.** Consequences found on a real iPhone across four release candidates (`litesync:docs/releases/0.19.0-rc.2.md` to `rc.5.md`, `litesync:src/token-prompt-modal.ts:3-26`): the text field is treated as the username and loses third-party keyboards (no Chinese input); the password manager fills the entry's username into any visible text field in the document, including one in a modal underneath (a vault was renamed to a password-entry name); the password keyboard has no dismiss key and covers the modal's buttons, so Enter must submit (`enterkeyhint="go"`); auto-focusing a password field on mobile pops that keyboard over everything. Their fix: a password field only ever in its own modal, fields underneath set read-only while it is open, and retries use the value captured before the modal opened. Trew has no password today, but the moment the invite or MCP token entry becomes `type=password` this applies; PLAN excludes iOS, but the same WebKit rules govern Obsidian on iPad for anyone who tries.
5. **iOS suspends background timers**, so interval sync is foreground-only and the reliable trigger is `visibilitychange` to visible, debounced (`litesync:src/main.ts:500-514`). Basalt already reconnects on foreground (`basalt:docs/design.md:183-186`).
6. **Go and JavaScript lower-case differently.** Checked here: `strings.ToLower("İ.md")` is `"i.md"`, while JS `"İ.md".toLowerCase()` is `"i̇.md"` (i plus combining dot). LiteSync folds in Go on the server (`litesync-server:internal/storage/canonical.go:14`) and in JS on the client (`litesync:src/utils/vault-path.ts:138-149`, which also strips trailing dots and spaces, which the server key does not), so client and server disagree about some collisions. Trew will have the same split if §4.1 of this report is adopted: one fold, specified in the fixtures, with vectors for U+0130, final sigma, and `ß`.
7. **A deadlock that `/health` could not see.** 0.17.1 fixed a production deadlock on the first real backup: the backup closure, running under the global lock, called a method that takes the same non-reentrant mutex. Every authenticated request hung while `/health` and static pages kept answering, so the server looked healthy. It survived six release candidates because the CLI and test doubles implemented the lock as a pass-through (`litesync-server:515ec64`). Two lessons: lock-holding code must be tested against the real lock, and a health probe that touches neither the lock nor the database says nothing (`litesync-server:internal/api/router.go:184-186`).
8. **Single-connection SQLite deadlocks on itself.** With `SetMaxOpenConns(1)`, any query through `s.db` while a transaction holds the connection waits forever; their code carries comments warning about it (`litesync-server:internal/sync/maintenance.go:218-220`, `internal/sync/service.go:378-379`). Basalt's store should keep a read pool separate from the writer; if it ever narrows to one connection, this becomes a class of bug.
9. **Remote deletions to trash.** `fileManager.trashFile` honours the user's deleted-files preference; `adapter.trashSystem` is unavailable on mobile, so the fallback is `adapter.trashLocal`; if trashing fails the file is kept and marked "pending delete" so the scan does not re-upload it (`litesync:src/sync/pull.ts:940-966,1066-1080`).
10. **Obsidian mobile and `.obsidian`.** They never sync the config directory on mobile, whatever the setting, and always exclude `workspace.json`, `workspace-mobile.json` and their own plugin directory (`litesync:src/main.ts:516-519`, `litesync:src/utils/ignore.ts:1-45`). Consistent with PLAN's refusal of config sync.
11. **CDN caching of server-served pages.** Cloudflare kept serving old web assets after an upgrade, and one full acceptance round of "bugs" was a stale image tag (`litesync:AGENTS.md` §10, `litesync-server:08629b8`). If Trew serves any page (landing page, history viewer), send ETag with `no-cache`, and make `doctor` report the running version.
12. **Shell scripts in CI.** macOS bash 3.2 reads the first byte of a full-width character after `$VAR` as part of the variable name (`litesync:fa4e393`), and multi-line `adb shell` commands are executed line by line, breaking quoting (`litesync:ff175bb`, `2fd2003`). Put probe logic in script files, which is our own shell-quoting rule.

## 6. Their bugs or weaknesses we must not repeat

1. **Merge bases disappear within minutes.** The merge base is whatever server history holds at the tracked revision (`litesync:src/sync/auto-merge.ts:44-55`). History is pruned by count (100 versions per Markdown file) and by age (90 days, measured from the version's creation) **inside every upload transaction** (`litesync-server:internal/sync/service.go:652-667,1509-1538`), not only in daily maintenance. At a 3 s edit debounce, 100 versions is about five minutes of typing on another device. Verified: against their server with default settings, uploading 100 edits after revision 1 makes `GET /version?revision=1` return 404. An offline phone that comes back then has no base, so a concurrent edit becomes a conflict copy instead of a merge. Age-based pruning has the exact flaw PLAN §4.5 describes: edit a note untouched for 91 days and the displaced version is deleted in the same transaction. This is independent, running evidence for PLAN §4.5's pinned survivor set, and an argument to extend it to device merge bases (§4.2 of this report, §8 below).
2. **Pruning on the write path.** Beyond losing bases, it deletes history and garbage-collects blobs inside the commit of an unrelated write, so a sync write can fail because pruning failed. Durability rules 3 and 5 both argue against it. Purge in Trew stays an explicit or scheduled operation with a dry run (PLAN §4.5).
3. **A merge that combines edits nobody wrote.** Run under `tsx` against their `smartThreeWayMerge` (clean in every case below): base "The meeting is on Monday at 10.", local "Tuesday at 10", remote "Monday at 11" merges silently to "Tuesday at 11" (token-level diff3, `litesync:src/merge/token/three-way-token.ts:16-31`, applied to line conflicts at `litesync:src/merge/smart-merge.ts:135-141`); edits to adjacent lines merge with no conflict, where git's diff3 would report one (`litesync:src/merge/three-way.ts:56-68`); a list where one side deleted an item and the other appended one merges, which is fine, but when the base is missing the resolver merges against `""` (`litesync:src/conflict-ui/conflict-actions.ts:48-56`), so two lists are unioned and **an item one side deleted comes back**, reordered (`litesync:src/merge/markdown/lists.ts:64-99`). This is the failure Basalt's merge header describes as "every inserted word can survive while the note's meaning is destroyed" (`basalt:client/src/core/merge.ts:48`), and it is why PLAN §2.6 refuses a second merge implementation. Keep Basalt's gated merge.
4. **A conflict freezes the path in both directions until a person acts.** An unclean merge records a pending conflict; from then on pull skips remote changes for that path (`litesync:src/sync/pull.ts:892-893`) and push skips local ones (`litesync:src/sync/push.ts:384,661`) until the resolver is opened. On first join in "merge" mode, every differing Markdown file becomes such a conflict (`litesync:src/bootstrap/bootstrap-manager.ts:318-322`). For Trew this is the wrong model: an agent edit to a frozen note never reaches that device, and a phone user may not open a resolver for days. PLAN §4.6 (merge or keep both, never block) is right.
5. **The "atomic" install is followed by a non-atomic rewrite.** After renaming staging into place and verifying the bytes, the committer calls `adapter.writeBinary(path, after, { mtime })` to set the mtime (`litesync:src/sync/local-commit.ts:259-266`), which rewrites the whole file in place, fires a second `modify`, and reopens the half-written-file window the staging step existed to close. The install itself moves the live note out to `recovery/` and renames staging in (`:205-235`), so Obsidian sees a delete and a create for an open note, and the precondition check (`:175-184`) reads disk, not the editor buffer: unsaved editor text is not protected. Basalt replaces text through `vault.process()` with a backup (reuse-map, plugin `vault.ts`); that choice stays.
6. **Documented properties that the code does not have.** The README says every vault has its own write lock so one tenant's slow upload cannot block another (`litesync-server:README.md:229-232`); `vaultMu` exists and is tested (`internal/sync/vault_state.go:26-38`, `vault_state_internal_test.go`) but no production path calls it: `Upload` takes the global `s.mu` (`internal/sync/service.go:466`). The plugin README says "no content is ever lost" while §6.3 shows a merge that manufactures text. Treat their docs as intentions, as the brief warned.
7. **Dedupe trusts size.** When an uploaded blob already exists, the stored copy is accepted if its size matches; content is re-hashed only with `OBSYNC_STRICT_BLOB_VERIFY` (`litesync-server:internal/storage/blobs.go:188-209`), so a bit-rotted blob of the right size silently absorbs the fresh, verified upload that could have repaired it. Their scrub samples 8 heads per run (`internal/sync/maintenance.go:150-172`). For Trew: when a device uploads a body for a chunk name the store already holds, it costs little to keep the verified bytes if the stored copy fails a check, and `verify -deep` must cover everything, not a sample.
8. **Whole-state writes on every edit.** Each queued operation awaits `store.save()`, which serialises the entire state (every tracked file's `FileState`, up to their 20,000-file limit), writes it, and reads it back to verify (`litesync:src/state/store.ts:433-470`, `litesync:src/sync/queue.ts:111-114,161-178`). That is a multi-megabyte write and read on every Obsidian save, on a phone. Basalt's index journal is the right shape.
9. **Quadratic collision checks.** `collidingPath` folds every tracked path for every incoming upsert (`litesync:src/state/store.ts:645-653`), so a snapshot resync of N changes over N files does N² folds. Found by reading, not measured; keep a folded-key index if Trew adds a similar check.
10. **Whole files everywhere.** Uploads, downloads, history and share bundles hold whole files in memory on the client, with a warning above 50 MB on mobile (`litesync:src/sync/push.ts:378-395`). Every edit of a large attachment stores a new full copy. This supports PLAN §2.2's decision to keep chunking.
11. **Everything serialised through one mutex and one connection**, including authentication (which writes `last_seen_at` on every request, `litesync-server:internal/sync/devices.go:172-191`) and each file's retention transaction during maintenance. Fine at their declared scale (one user, 10 devices, 20,000 files), and the reason for the deadlock class in §5.7 and §5.8. No rate limiting on failed authentication exists anywhere in `internal/api/auth.go`.

## 7. Where they contradict our plan, and who is right

| Topic | LiteSync | Trew plan | Who is right |
|---|---|---|---|
| History retention | Age (90 d) and count (100) per file, pruned inline on every upload | Pins by reference from the displacing operation; purge explicit (PLAN §4.5) | **We are**, demonstrated by §6.1. We should go further and pin device merge bases. |
| Merge policy | Aggressive auto-merge (token, list union, adjacent lines), then a blocking resolver | Basalt's gated merge, else conflict copy, never blocking (PLAN §2.6, §4.6) | **We are.** Their merge fabricates text (§6.3); blocking is incompatible with unattended agent writes. Their resolver UI is a nice optional layer over conflict copies, later. |
| Transport | REST, 30 s polling, 3 s after edits | WebSocket with live fan-out (PLAN §1, §3.4) | Both defensible. Polling is simpler and is part of how they fit in 256 MB, but an agent edit should reach an open laptop in seconds, and Basalt's socket machinery already exists. Keep ours. |
| Content storage | Whole-file blobs | Content-defined chunks, SHA-256 of raw bytes (PLAN §2.2) | **We are**, for large attachments and mobile memory (§6.10). |
| Path collisions | Server refuses case-fold and NFC collisions with a unique index | Server refuses non-NFC paths; folding only in the client engine (PLAN §4.1) | **They are.** Adopt, because MCP creates paths with no filesystem in the loop (§4.1 of this report). |
| Rename model | Server-side `file_id`; rename is a metadata update with CAS | Path-keyed entries with a rename chain (Basalt protocol 7) | Neither is clearly wrong. Their identity model makes rename history continuous, but it cost them four rounds of rename bugs (§5.3, `litesync:docs/releases/0.17.0-rc.3.md`). Not worth reopening the protocol. |
| Device credential storage | `app.secretStorage`, never in `data.json` | `data.json` (reuse-map, plugin persistence) | **They are**, subject to the minAppVersion cost (§4.11). |
| Deletion-entry purge | Gated on the minimum acked sequence of non-revoked devices | Deletions are entries (rule 6); purge keeps heads and renames | Compatible. If Trew ever purges deletion entries, use their gate. |
| Health | `/health` returns a constant | `/health` inherited, explicitly not a vault verdict (PLAN M5.5) | Same shape, and their incident is the argument for adding a bounded lock and database probe (§8). |

## 8. Concrete recommended changes to PLAN.md

- **§4.5, survivor set:** add "for each path, every version that was head at or after the minimum applied checkpoint of non-revoked devices (a device's possible merge base)". Cite this report §6.1. Add to M5 item 10: "a device offline across 100 edits by another device and a default purge still merges, it does not make a conflict copy".
- **§4.5:** state that pruning never runs inside a write transaction; purge and orphan reclamation are separate operations with a dry run.
- **§4.1 and protocol.md "Paths":** add "a create or move whose folded key (NFC then one specified case fold) equals that of a different live path is refused with a new `collision` code". It applies to device `put`, MCP `create_note`, and moves. Put the fold in `protocol-fixtures.json` with vectors for U+0130, `ß`, and final sigma, and have both Go and TypeScript consume them (§5.6).
- **§4.5 / M5.5, orphan chunk reclamation:** two persisted rounds, an age gate longer than the longest upload-to-commit window, final check under `commitMu`, and skipped while backup or verify runs.
- **§8 rule 2 / M5.5:** a chunk that fails verification is quarantined, not deleted, and reads return a typed `corrupt` error, never `notfound`. `doctor` lists quarantined chunks.
- **M5.5 observability:** `/health` (or `trew health`) acquires the commit lock and runs a trivial read with a timeout and reports failure; add a test that runs backup against the real `commitMu`, never a pass-through double (their 0.17.1 incident).
- **protocol.md handshake:** `hello` carries `clientVersion` and `platform`; the devices table stores them; `doctor` and `devices` show them; revoked devices stay listed.
- **M4/M5 tests:** an authorization matrix generated from the MCP tool registry and the control-socket command table (no token, expired, revoked, read, write) so a new tool cannot ship unenforced.
- **M2 plugin tasks:** (a) persistent notices for credential refusal and stranded paths on mobile, where there is no status bar; (b) a lifecycle test "rename a note that is open in the editor, then keep typing" (§5.3); (c) decide whether the device token moves to `app.secretStorage`, after checking which Obsidian version introduced it; (d) adapt the platform probe (MIT, `litesync:src/diagnostics/platform-probe.ts`) as a command that writes to the plugin directory, and run it on the Android phones in M3.
- **M9 pairing:** decide between `obsidian://lyell?invite=` in the QR and an HTTPS landing page with the invite in the URL fragment (§4.8); write down the reason either way. If any credential field is ever `type=password`, it gets its own modal (§5.4).
- **plan/ideas.md:** add "frontmatter merge by key, evaluated against Basalt's merge fuzz corpus before any adoption" and "an optional resolver view over conflict copies". Explicitly refuse token-level and list-union auto-merge, citing §6.3.
