# Pumice (search5/pumice + search5/pumice-server)

Investigated 2026-09-22. Client `search5/pumice` at `5c5b844` (plugin 0.0.36, 144 commits since 2026-03-24, real work from 2026-07-09). Server `search5/pumice-server` at `f2654fa` (0.2.9, 111 commits since 2026-07-12). Both repos cloned under the session scratchpad. Neither repo has any GitHub issues or PRs; all evidence below is code, commit messages and docs. Citations: `pumice:` is the client repo, `pumice-server:` the server repo.

## 1. Summary

- **What:** an Obsidian plugin plus a Python server for self-hosted sync, per-file version history, an Obsidian Publish clone (sites, custom domains, collaborators), cross-account vault sharing, optional E2EE, and, notably, an MCP endpoint with read and write tools over the synced vault. It is the closest functional sibling to Telimus found so far: a plaintext-capable server with a built-in MCP.
- **Maturity:** about six weeks of intense work, almost entirely AI-generated (commits carry `Co-Authored-By: Claude Sonnet 5`, comments are essays). No issues, one star, zero users visible. It works in the author's own deployment (`pumice.flask.moe` is mentioned in `pumice:14deca4`), but the sync core has data-loss and security defects listed in §6.
- **License:** client is **BSD 3-Clause** (`pumice:LICENSE`, "Copyright (c) 2026, Jiho Persy Lee"). Server has **no license file and no license field** (`pumice-server:pyproject.toml`, `gh repo view` reports `licenseInfo: null`): all rights reserved, **ideas only, never copy**.
- **Stack:** client TypeScript, esbuild, vitest, `node-diff3`, `diff`; minAppVersion 1.13.4. Server Python 3.13, Twisted asyncioreactor, autobahn WebSocket, Pyramid, SQLAlchemy (SQLite, MySQL, Postgres, CUBRID), official `mcp` SDK, Jinja2, Babel.
- **Verdict:** little code worth taking (the client is BSD but its sync engine is weaker than Basalt's in every dimension). High value as a record of *what goes wrong*: the gRPC-Web to WebSocket history, a set of real Obsidian platform quirks, a whole-file MCP writer with no preconditions, and a publish feature that shows exactly which security traps a "server that has the notes" walks into.

## 2. Architecture in brief

**Storage.** The server keeps each vault as a plain directory of files: `data_dir/vaults/{owner}/{vault_id}/...` (`pumice-server:service.py:94-100`). SQLite (or another RDBMS) holds `file_metadata` (path, mtime, size, sha256, is_deleted), `file_history` (one row per version pointing at a `.bak` file hard-linked from the live file), and an append-only `vault_change_log` (`pumice-server:repository.py:311-358`). History is whole-file, deduplicated only by hard links. There is no chunking. The vault's identity is its **folder name** (`vault.getName()`), paired with the account username (`pumice:README.md` "The vault's folder name is its identity on the server").

**Reconciliation is server-side and timestamp-based.** Every sync, the client hashes its vault (with an mtime+size keyed IndexedDB hash cache, `pumice:src/contentHashCache.ts`), adds tombstones it recorded from `delete`/`rename` events, and sends the whole list in `delta_req`. The server first **walks and hashes its own vault directory** (`_scan_and_merge`, `pumice-server:service.py:102-232`), treating any file that appeared or vanished on disk as a change, then compares per path: tombstone beats everything, otherwise differing hashes resolve by larger `modified_at_ms`, ties go to the client (`pumice-server:service.py:334-396`). The reply is two lists, `needUpload` and `needDownload`.

**Transport (current).** One WebSocket at `/ws` per vault. First frame is `init` with the token, vault id, device name and `lastKnownChangeId`; server answers `init_ok`, then replays folded changes since that id as ordinary `push` frames, then `ready{latestChangeId}` (`pumice-server:ws_sync_resource.py:429-501`). JSON text frames `{op, payload}` with **no request id**; the client allows exactly one outstanding request (`pumice:src/wsTransport.ts:11-13`). Uploads are `push_req{path, contentHash, sizeBytes, modifiedAtMs}` then either `push_ack` (server already has that hash elsewhere, hard-links it) or `push_res{needData}` followed by **the whole file as one binary frame** (`pumice-server:ws_sync_resource.py:382-427`). Downloads stream `file_chunk_header`, 256 KiB binary frames, `file_chunk_eof`, and a final `stream_end`. Heartbeat: idle ping after 10 s, dead after 120 s, any single request older than 60 s tears the connection down (`pumice:src/wsTransport.ts:123-132`). A 30 s full sync runs regardless of push activity (`pumice:src/liveUpdates.ts:57`), and a 3 s debounced full sync runs after any local edit (`pumice:src/main.ts:1031-1033`).

**Conflicts are client-side.** When the server says download and a local file exists, the client fetches the version history for the path, downloads the version whose hash equals its recorded "last synced" hash, and runs `node-diff3` over local, base and remote (`pumice:src/syncClient.ts:598-630`). Clean merge: write the result and let the next sync upload it. Overlap: write git-style `<<<<<<<` markers into the note itself, after a `.sync-conflict-<ts>` backup. Non-text or no base: `server-wins` (backup local, overwrite) or `client-wins` (backup remote, skip).

**Everything else.** Publish is a separate REST upload path into `data_dir/published/...` gated on `publish: true` frontmatter (`pumice-server:web.py:946-1010`), rendered client-side by `publish_render.js` or server-side by Python-Markdown when server plugins are enabled. Vault sharing grants another account full sync on one vault (`vault_shares`, `sharedVaultOwner` setting). MCP at `/mcp` via the official SDK, Streamable HTTP with in-memory sessions, auth by the same device token or an OAuth 2.1 + DCR + PKCE flow that mints a device token (`pumice-server:oauth_server.py`, `web.py:623-760`).

### The gRPC-Web history, and why they left

This is the part most relevant to our WebSocket choice. The sequence, from commit messages:

1. **gRPC-Web first** (protobuf, `grpc-web`/`google-protobuf`, `protoc` in the build). One HTTP request per RPC.
2. **No client streaming from a browser.** "Browsers can't client-stream via gRPC-Web/connect-es, so large uploads had to be fully batched in memory before sending" (`pumice:ec0805a`). They bolted on a raw `fetch()` + `ReadableStream` duplex path with gRPC-Web fallback and a separate Twisted streaming endpoint with its own auth and timeouts (`pumice-server:7a95ff0`). `requestUrl` cannot stream, so this also needed a lint exception for `fetch` (`pumice:215fb61`).
3. **No server push.** They added SSE at `GET /watch` as a second connection. Native `EventSource` cannot set `Authorization`, so they hand-rolled a fetch-based SSE reader (`pumice:7a70ab9`), then needed a CORS preflight fix (`pumice-server:cfb53d7`), then hit an infinite notify, resync, notify loop because a dict-shape mismatch made every Delta look like a change (`pumice-server:33a28b2`).
4. **Build and review friction.** Generated protobuf stubs were committed, reverted and half-committed three times for the Obsidian review bot (`pumice:c6163ed`, `a273ed4`, `db48e4f`). The bundle was 303 KB; after removing gRPC it is 158 KB (`pumice:1bb58e3`).
5. **The switch** (2026-08-12 to 08-15, `pumice-server:2056c3d` through `cdab4f4`): one persistent WebSocket replacing gRPC-Web, SSE and protobuf, "modeled on Obsidian core's own built-in Sync plugin (analyzed from the shipped app, not copied)" (`pumice-server:ws_sync_resource.py:1-9`). They then re-read `obsidian.asar` twice more and deliberately **removed** request-id multiplexing to match core Sync's one-request-at-a-time design (`pumice-server:2802bf6`).

**The lesson for us.** Our WebSocket decision is confirmed from the opposite direction: every capability they had to add around gRPC-Web (client streaming, push, a single authenticated session, reconnect catch-up) is what Basalt's protocol already has. But their *second* move, dropping request ids to imitate core Sync, cost them three bugs in a week: a stray keepalive `pong` resolving the wrong request (`pumice:14deca4`), requests hanging after a queue slot was clobbered (`pumice:f1d82f1`), and interleaved multi-file download frames that could not be demultiplexed (`pumice-server:3df6157`). Without ids, a single timed-out request has to kill the whole connection because a late reply would be misattributed (`pumice:src/wsTransport.ts:128-132`). Keep Basalt's `id` on every request and response (`plan/protocol.md` "Handshake"), and keep chunk bodies bound to the request they answer.

## 4. Ideas worth adopting

1. **Publishing is an explicit act that pins content, not a live view of the store.** Pumice copies a note into a separate published tree only when the user publishes it (`pumice-server:web.py:946-1010`), and requires `publish: true` in the note's own frontmatter before a single-file publish is accepted (`pumice:README.md`, "Publish current file requires publish: true"; rationale in `pumice:3768462`). For Telimus the equivalent is cheap and much safer than "serve a folder": a `published` table of `(path, uid)` pins, created only by a device session, so an agent edit, a half-written note, or an injected instruction in a note never goes live by itself. Lands in `plan/ideas.md` "Publishing" (replace "serve a folder or a tag" with "serve pinned versions"); add to PLAN §4.5 that published pins are retention pins.
2. **MCP authorship shows up in version history.** Pumice labels MCP writes `device_name="MCP"` in history (`pumice-server:mcp_tools.py:379-381`). We already plan author rows (PLAN §2.3, §2.4); this confirms the history panel is where users look for it.
3. **An OAuth flow that is only a consent wrapper around minting an ordinary token.** Pumice's OAuth 2.1 (RFC 9728 metadata, RFC 8414, RFC 7591 DCR, PKCE) never creates a second credential type: a successful exchange calls `create_device_token()` and the result is revocable in the same device list (`pumice-server:9c5b941`). They also found that a failed PKCE check must not consume the authorization code, or one bad request locks out the legitimate client (same commit, `peek()` then `consume()`). If PLAN §2.3's "no OAuth" is ever revisited (`plan/ideas.md` "Reconsider OAuth, deliberately"), this is the shape: OAuth mints an `mcp_tokens` row with scope `read` by default, expiry, and label from the DCR `client_name`, and DCR registrations are shown on the consent page with their redirect URI.
4. **Size, purge and usernames as first-class ops.** They are cheap and they are what a devices panel needs (`pumice-server:service.py:799-845`). Our `vault_status` MCP tool covers size; the plugin panel could show vault bytes and history bytes from the same query. Low priority.
5. **Connection status belongs in the settings tab, not only the status bar,** because Obsidian mobile hides the status bar by default (`pumice:src/settingsTab.ts:105-113`). Basalt's panel already carries the state; keep it visible there in M2 task 7.
6. **Refuse over-limit uploads before any I/O and advertise the limit in the handshake.** They lost this check once during a refactor and found it again only in cleanup (`pumice-server:cdab4f4`). We already advertise `perFileMax` in `ready` (`plan/protocol.md` "Device session"); add a regression test that a `put` whose declared `size` exceeds it gets `toolarge` before any `want`.

## 5. Gotchas and platform quirks they discovered

Each item has evidence in their tree. Where the claim is about Obsidian core internals learned by reading `obsidian.asar`, it is labelled as their claim.

1. **WebSocket `binaryType` defaults to `"blob"`** in both browsers and Node, so binary frames arrive as `Blob`. Set `"arraybuffer"` on connect (`pumice:src/wsTransport.ts:181-185`, `pumice:956db01`). Basalt's transport should already do this; verify in M0.5 against the Node `ws` build too.
2. **Mobile browsers drop a script-triggered navigation to `obsidian://`** once the user gesture is consumed by an `await`, with no error. Their login page shows a link to tap instead of redirecting (`pumice-server:src/pumice_server/static/login.js:95-107`). Relevant if Telimus ever hands anything back to the plugin from a web page, and a reason to keep pairing as QR or paste.
3. **Obsidian's Settings modal hijacks Tab** on an ancestor container and turns it into row navigation, calling `preventDefault()` unconditionally (`pumice:src/settingsTabKeyboard.ts:1-14`).
4. **`App#saveLocalStorage` is vault-scoped by key prefix** (observed as `<16-hex vault hash>-key`) and does not interoperate with raw `localStorage` (`pumice:src/tokenStore.ts:19-27`, `pumice:215fb61`). Corollary they missed (§6): IndexedDB is **not** vault-scoped.
5. **Raising `minAppVersion` strands mobile users.** Bumping to 1.13.0 "broke updates for anyone still on an older Obsidian mobile build (confirmed: 1.12.7 was current on mobile as recently as March 2026, only two months before 1.13.0 shipped)" (`pumice:cc33a58`). They went back to 1.12.7 with a dual settings tab, then later jumped to 1.13.4 anyway (`pumice:ea6c3f1`).
6. **Never lower a released version number.** `pumice:versions.json` lists `0.1.0` through `0.1.18` and then `0.0.10` through `0.0.36`: they renumbered downward, so any install on 0.1.18 sees 0.0.36 as older and never updates.
7. **Setting mtime out of band leaves `TFile.stat` stale.** Using `fs.utimesSync` after a write meant every synced file missed the hash cache next scan; pass `mtime` through the Vault write's `DataWriteOptions` instead (`pumice:c8af851`, `pumice:src/syncClient.ts:130-144`). Basalt already passes times through the adapter (`basalt:client/src/plugin/vault.ts:1564`).
8. **Config-dir paths get no vault `delete` or `rename` events and are not TFiles.** Plugin removals under `.obsidian/plugins` can only be detected by diffing directory listings between syncs (`pumice:src/syncClient.ts` `detectRemovedPluginPaths`, `pumice:src/main.ts:77`). `vault.createFolder` cannot create config-dir folders; `adapter.mkdir` level by level is needed (`pumice:src/syncClient.ts:156-170`). Confirms our refusal of config sync (PLAN §1 "Scope and refusals").
9. **Obsidian community review checklist**, as they received it: `requestUrl` not `fetch`, `App#saveLocalStorage` not `localStorage`, popout-window-safe timers, `Vault#configDir` not `.obsidian`, `FileManager.trashFile` not `Vault.delete`, `instanceof TFile` not casts, no Node `fs`/`child_process` (mobile), a Component-lifecycle leak in `MarkdownRenderer.render` (`pumice:ab64f3f`, `pumice:215fb61`). `eslint-plugin-obsidianmd` flags deprecated `display()` and `setWarning()` and blocks disabling `no-deprecated` by comment (`pumice:b692f4d`). Useful as an M9 pre-submission checklist.
10. **Mobile modal layout.** `.modal-content` collapses to zero height for some core class combinations on mobile, and the bottom toolbar overlays the last row in a way `vh` and `env(safe-area-inset-bottom)` do not account for (`pumice:0b27972`, `pumice:8564fbd`, `pumice:af53f59`).
11. **Core Sync's own icons (`sync-small`, `check-small`) are registered by the Sync plugin and unavailable to community plugins** (`pumice:56b70d7`); use base lucide names.
12. **Their reported core Sync behaviour** (their claim, from reading `obsidian.asar` 1.13.6): auth in the first WebSocket message, one outstanding request per connection, a fixed 30 s `requestSync` interval, reconnect backoff with ±50% jitter, per-file metadata in push frames, content-hash dedup on push, a 60 s request timeout (`pumice-server:e4fb1ab`, `pumice:f1d82f1`, `pumice:src/liveUpdates.ts:40-57`). We should not base anything on reverse-engineered proprietary code, but the jitter point is independently good practice: check Basalt's reconnect applies jitter per attempt.
13. **An init handshake with no timeout hangs forever** when the server accepts the socket and never answers (`pumice:782d97b`). Basalt has a hello deadline; keep a client-side one too and test it with a server that accepts and stays silent.
14. **Changing the server address must drop the cached connection,** or "Test connection" waits on the old one (`pumice:b25dc43`).
15. **Self-written files fire `create`/`modify`/`delete` like user edits.** They track a `selfWritePaths` set to avoid re-arming sync on their own downloads (`pumice:31e4fe1`, `pumice:src/main.ts:299-360`). Basalt solves this in its preserving-write adapter; worth a regression test that a download does not schedule an upload.
16. **Auto-created "Untitled" notes are renamed immediately,** which their rename handler special-cases with a localized regex `^(Untitled|무제)(\s+\d+)?$` (`pumice:src/main.ts:321-330`). The special case itself is a bug (§6), but the observation (a rename storm right after note creation) is real.
17. **App secret storage.** `app.secretStorage.setSecret/getSecret` works on desktop and mobile with no platform code, available since 1.11.4 per their commit (`pumice:c8af851`, `pumice:src/tokenStore.ts:1-55`). They clear a secret by setting `""` (`pumice:src/tokenStore.ts:37`) and use the unprefixed id `sync-token`, which invites collisions if ids are not per-plugin.
18. **Declarative settings.** `getSettingDefinitions()` (1.13.0+) replaces `display()`, makes every setting searchable from Obsidian's global settings search, and per their comment `display()` is never called while it returns a non-empty array (`pumice:src/settingsTab.ts:33-37`). `render:` escape hatches allow custom rows; `update()` rebuilds the tab from the definitions. `setDestructive()` replaces `setWarning()` (`pumice:ea6c3f1`). This is the main reason for their 1.13.4 floor; secret storage alone needs only 1.11.4.

## 6. Their bugs or weaknesses we must not repeat

Data loss and integrity:

1. **Deletion always wins, regardless of age.** If the client sends a tombstone and the server copy is live, the server deletes it immediately, with no comparison against the tombstone time or the server version (`pumice-server:service.py:364-376`). A phone that was offline for a week and deleted a note deletes every newer edit made elsewhere. The content survives only in server history. Our conditional writes (`base`/`prevBase`, `plan/protocol.md` "Writing") exist precisely for this.
2. **Last writer by device clock wins at the server.** Differing hashes resolve by `modified_at_ms` (`pumice-server:service.py:385-396`), and upload has no base precondition (`finalize_pushed_file`, `pumice-server:service.py:404-484`). If the device with the later mtime is the one uploading, the other device's edit is overwritten on the server without any merge; the 3-way merge only runs on the *downloading* side. Clock skew decides whose work survives. PLAN §4.11 "Clocks" is right to keep mtimes as metadata only.
3. **Rename is delete plus create, with no source precondition.** A rename on device A deletes the old path on the server even if device B edited it a moment earlier (item 1), and history does not follow device renames (only the MCP `rename_note` relabels history, `pumice-server:5b82165`). Their `tombstones_by_hash` rename detection was dead code all along (`pumice-server:2a3844e`). Basalt's `prevBase` covers this.
4. **Conflict markers are written into the note.** Overlapping edits produce `<<<<<<<`/`=======`/`>>>>>>>` inline in the live file (`pumice:src/syncClient.ts:720-740`), which then syncs to every device and is served to MCP and to published pages. Keep Basalt's conflict copies (PLAN §4.6).
5. **Merge decodes with a non-fatal `TextDecoder`.** Any invalid UTF-8 in a "text" extension becomes U+FFFD and the merged result is written back (`pumice:src/syncClient.ts:615-619`). Text is decided by extension only (`pumice:src/textFileTypes.ts`). Basalt's merge validity gates must keep refusing non-UTF-8.
6. **Staging files inside the live vault directory.** Uploads write `note.md.tmp-<hex>` next to the target (`pumice-server:service.py:421`), and every Delta walks that same directory (`service.py:110-181`). A concurrent scan from another device can record the temp file as a real note, notify every device to download it, then tombstone it. Replacement is `os.remove` then `os.rename` (`service.py:439-441`), a non-atomic window where the file does not exist; no `fsync` anywhere. Our path rules already forbid the `.telimus-tmp-` mark (`plan/protocol.md` "Paths"), and Basalt's store never stages inside a scanned tree.
7. **Filesystem and database commit separately.** File bytes are renamed into place, then metadata, journal and history are committed (`service.py:439-474`); `_scan_and_merge` saves metadata and then writes one journal row per change in separate transactions (`service.py:217-231`). A crash between them loses the journal row, so reconnect catch-up silently misses that change; they rely on the 30 s full resync to paper over it. Rule 1 (acknowledge only after durable) and a single transaction for entry plus log are the fix we already have.
8. **Catch-up gap.** `init` reads `get_changes_since`, then reads `get_latest_change_id`, then subscribes to live changes (`pumice-server:ws_sync_resource.py:481-501`). A commit landing between the first read and the subscription is neither replayed nor pushed, yet `latestChangeId` covers it, and the client persists that id on `ready` before it has applied anything (`pumice:src/main.ts:466`). Also, pushed changes that arrive while a sync is running are simply dropped (`pumice:src/main.ts:774-777`). Basalt's covered-range continuity check (design rule 3) is the correct design; keep it and keep the cursor advancing only on apply.
9. **Live pushes are sent from worker threads.** `finalize_pushed_file` and `_scan_and_merge` run under `asyncio.to_thread` and call `change_notifier.notify_change`, whose callback calls autobahn `sendMessage` (`ws_sync_resource.py:403-420`, `service.py:476-477`, `ws_sync_resource.py:555-567`). Twisted transports are not thread-safe; frames from two threads can interleave on one socket, and the listener dict is mutated without a lock. Our hub must hand fan-out to each session's own writer goroutine (Basalt does).
10. **Whole file in one binary frame, whole file in memory, with a 2 GiB default cap** (`pumice-server:service.py:37`, `ws_sync_resource.py:413-419`, `pumice:1bb58e3` "WS sends a whole file as one frame"). A large attachment is a 2 GiB allocation on both sides. Our 1 MiB chunks and `perFileMax` are right.
11. **O(vault) work on every edit.** Each local edit triggers, after 3 s, a full client scan plus a server-side `os.walk` and stat of the entire vault (`pumice:src/main.ts:1031`, `pumice-server:service.py:315`), and every device repeats it every 30 s. Our cursor-based catch-up makes the steady state O(changes).
12. **The "Untitled" rename special case resurrects notes.** A synced `Untitled.md` renamed to a real name leaves no tombstone (`pumice:src/main.ts:321-330`), so the server keeps `Untitled.md` and sends it back.
13. **Per-device IndexedDB stores are not per-vault.** `pumice-last-synced-hash`, `pumice-content-hash-cache` and `pumice-local-snapshots` are fixed names keyed only by path (`pumice:src/lastSyncedHashStore.ts:11`, `contentHashCache.ts:27`, `localSnapshotStore.ts:36-39`), on the stated belief that IndexedDB is "already isolated (origin-scoped) per vault". On desktop every vault shares one origin, which is why core uses an app-id prefix and why `saveLocalStorage` prefixes keys (§5 item 4). Two vaults with `Daily/2026-09-22.md` share one merge base. Basalt keeps its index as files in the plugin directory; if Telimus ever moves state to IndexedDB, key it by vault id.

Security:

14. **Path traversal on upload.** `push_req.path` is joined onto the vault directory with no containment check (`pumice-server:service.py:419-421`, and `finalize_deduped_file` at `:493-499`). `../../other_user/Vault/x.md` writes into another account's vault, or anywhere the process can write. They fixed the same bug in restore (`pumice-server:3d00ff6`) but not here. `_get_vault_path` uses a bare `startswith` without a separator, so a user can reach vaults of an account whose name has theirs as a prefix (`service.py:96-98`); the published-file upload has the same prefix bug (`web.py:977-980`). Our server-side path validation (PLAN §4.1) must be one function called by every write path, including MCP and restore, with a fixture per entry point.
15. **Unconditioned `obsidian://` credential handler.** `obsidian://pumice-auth?token=...` saves any token it is handed, with no nonce and no confirmation (`pumice:src/main.ts:163-184`). Any web page or message can switch the plugin to an attacker's account, after which the victim's vault uploads there. The login page also appends the device token to an unvalidated `redirect` parameter (`pumice-server:static/login.js:59, 90-103`), a phishing path for tokens on the real domain. Basalt's handler already opens a modal rather than pairing (`basalt:client/src/plugin/main.ts:449-462`); Telimus must keep that, and the modal must show the server URL from the invite string prominently, since our invite carries its own server URL (`plan/protocol.md` "The invite string") and a malicious QR would pair the device to a hostile server.
16. **Device tokens stored in plaintext as the primary key, never expiring** (`pumice-server:repository.py:389-393`, `README.md` "device tokens don't expire"). Our hashed tokens with MCP expiry (PLAN §2.3) are right.
17. **Publish site passwords are stored in plaintext and never enforced.** `passwords.json` is written and listed (`pumice-server:web.py:1743-1770`) and nothing else in the server reads it: a "password-protected" site is public.
18. **User-controlled script and HTML on the server's own origin.** `publish.js` from the vault root is loaded on every page of a site with a custom domain, "including the old `/publish/{username}/{vault}/...` path" (`pumice-server:docs/PUBLISH_JS.md`, `web.py:1294`), which is the same origin as the dashboard and its session cookie. Vault collaborators and the MCP `write_note` tool can both write that file. The server-rendered path runs Python-Markdown without a sanitizer (`web.py:1411-1415`), which passes raw HTML through, and the client renderer escapes text but emits `[x](javascript:...)` links unchanged (`pumice-server:client/publish_render.ts:894-895`). Any publishing we do must serve from a separate origin with a strict CSP, sanitize HTML, and never execute vault content.
19. **MCP `write_note` is a whole-file blind overwrite** with no base version, no preview, no idempotency, and tool results that return note text with no untrusted-content boundary (`pumice-server:mcp_tools.py:326-389`). An MCP rename was invisible to reconnect catch-up for a release because MCP tools mutated metadata outside the service path (`pumice-server:2802bf6`). This is the exact failure PLAN §2.4 designs against (one commit path for devices and agents) and §4.4 refuses; Pumice is the worked example of why.
20. **CORS on `/mcp` reflects any `Origin` with `Allow-Credentials: true`** (`pumice-server:mcp_resource.py:84-91, 119-122`). Not exploitable today because MCP only accepts a bearer header, but it is the wrong default; our `--allow-origin` list (plan/mcp-tools.md "Authentication and authorship") is right.

## 7. Where they contradict our plan, and who is right

| Topic | Pumice | Telimus plan | Who is right |
|---|---|---|---|
| Request ids | Removed to match core Sync; one request at a time | Every op carries `id` (`plan/protocol.md`) | **We are.** Their own history is three bugs in a week and a design where a timeout must kill the socket (§2 lesson). |
| Server storage | Plain file tree per vault, server rescans it every Delta | Content-addressed chunk store, SQLite metadata, versions | **We are.** Their tree makes the server a sync peer racing its own writers (§6 items 6, 7). Their one real advantage, a browsable folder on the server, is our headless-client sidecar (PLAN §4.7) or a later `--export-dir` (`plan/ideas.md`). |
| Conflict decision | Server picks by device mtime; merge only on the downloading side | Conditional writes by version UID, `stale`, conflict copies | **We are.** §6 items 1 to 3. |
| Conflict presentation | Inline git markers in the note | Conflict copies (PLAN §4.6) | **We are,** doubly so with an agent and publishing reading the same file. |
| Chunking | None; whole-file frames, 2 GiB cap | 1 MiB chunks, 64 MiB `perFileMax` | **We are.** |
| Catch-up | Change-id replay plus a 30 s full resync to cover gaps | Cursor with covered ranges, no periodic full scan | **We are,** provided our continuity check is tested against the gap in §6 item 8. |
| MCP writes | Whole-file `write_note`, no base | Exact edits with `base` UIDs, no whole-file writer in v1 (PLAN §4.4) | **We are.** |
| MCP auth | Same device token, or OAuth 2.1 + DCR minting one | Separate `mcp_tokens` with scope and expiry, no OAuth (PLAN §2.3) | **We are for v1.** Their design gives every MCP client full read-write power of a device token with no expiry. If OAuth is ever added, adopt their "OAuth mints an ordinary token" shape, but mint a scoped `mcp_tokens` row (§4 item 3). |
| Scope | Multi-account, vault sharing, site collaborators, E2EE | One person, one vault, no teams | **We are,** for this project. Their sharing features are where most of their authorization code and several of their bugs live. |
| Vault identity | Folder name | Vault id in the invite | **We are.** Theirs silently forks a vault when a folder is renamed and collides on "Obsidian Vault". |
| Publishing | Explicit upload of a copy, frontmatter-gated | Idea: serve a folder or tag from the store (`plan/ideas.md`) | **They are, on this one point.** Publishing should pin explicit versions rather than expose the live store; adopt it (§4 item 1). Their implementation (same origin, unsanitized, unenforced passwords) is not to be copied. |
| minAppVersion | 1.13.4 for declarative settings | Basalt's 1.7.2 | **We are, for now.** Their own commit shows the cost to mobile users. Secret storage can be feature-detected without a floor bump (§8). |
| Token storage | `app.secretStorage` | Device token in plugin `data.json` (reuse map `DeviceConfig`) | **They are.** A device token in `data.json` travels with any backup, git or file-sync of `.obsidian`. Adopt secret storage where available (§8). |

## 8. Concrete recommended changes to PLAN.md

- **§3.4 / `plan/protocol.md` "Design rules":** add a sentence that every request and response carries `id` and every body frame is bound to the request it answers, citing Pumice's removal of request ids and the three bugs that followed (`pumice:14deca4`, `pumice:f1d82f1`, `pumice-server:3df6157`). This records why "simplify to one request at a time" is refused.
- **§4.1 Path policy:** state that containment is checked by one function after normalisation, and that *every* entry point that turns a wire path into a store key or filesystem path calls it: `put`/`putmany`, rename source and destination, restore target, MCP tools, and any publish or export path. Add a fixture per entry point with `..`, absolute paths, and sibling-prefix names (`alice` versus `alice2`). Pumice fixed traversal in restore and left it open in upload (§6 item 14).
- **M2 task 7 (plugin main.ts):** the `obsidian://telimus?invite=` handler must never pair directly; it opens the existing modal (Basalt already does, `basalt:client/src/plugin/main.ts:449-462`) and the modal shows the server URL and vault id decoded from the invite, with a warning when the URL is not the one already configured. Add a test that a protocol-handler call with a valid invite changes no config until the user confirms.
- **M2 task 5 (pairing.ts) and task 7:** store `deviceToken` in `app.secretStorage` when it exists at runtime, under a product-prefixed id such as `telimus-device-token`, falling back to `data.json` on older apps. Do **not** raise `minAppVersion` for it (Pumice's `cc33a58` shows the cost). Migration reads the old location once, writes the secret, verifies it reads back (rule 4), and only then removes the old field (rule 3). The headless client keeps its file config.
- **M1 hub and session:** add a test that fan-out never writes to a session's socket from any goroutine other than that session's writer, and that a commit racing a reconnecting session's catch-up is delivered exactly once (the Pumice gap in §6 item 8). Name it after the scenario: "commit between catch-up read and subscribe".
- **M1 commit path:** add a regression test that a device tombstone with a stale `base` does not delete a newer version made by another device (§6 item 1), and one that a rename whose source moved since `prevBase` is `stale` (§6 item 3). These are the two Pumice behaviours most likely to be reintroduced by a "simplification".
- **§4.6 Conflict copies and the agent:** add one line: conflict markers are never written into a live note, because the agent, search and any published page all read the live note.
- **§4.10 / plan/mcp-tools.md:** cite Pumice `write_note` (`pumice-server:mcp_tools.py:326-389`) as the concrete example of the failure §4.4 refuses: a plaintext-server MCP that overwrote whole files, bypassed the journal until a later fix (`pumice-server:2802bf6`), and returned note text without an untrusted boundary.
- **`plan/ideas.md` "Publishing":** rewrite as "serve pinned versions": a device-only `publish` op records `(path, uid)` pins (retention pins under §4.5), the note must carry `publish: true`, agents cannot publish, pages are served from a separate origin (or at minimum a path with a strict CSP and `sandbox`), Markdown HTML is sanitized, `javascript:` and `data:` link schemes are refused, and no vault file is ever executed as script. List Pumice's `publish.js`, unsanitized Python-Markdown and unenforced site passwords (§6 items 17 and 18) as the reasons.
- **`plan/ideas.md` "Share one note":** add that a signed link should also point at a pinned `uid`, not the live path, for the same reason; and that it is the first narrower reader, so PLAN §2.2's chunk-fetch authorisation note applies before it ships.
- **`plan/ideas.md` "Reconsider OAuth, deliberately":** add Pumice's shape (OAuth as a consent wrapper that mints an ordinary scoped token, `peek()` before `consume()` on code exchange, DCR `client_name` and redirect URI shown on the consent page) as the design to use if it is reopened.
- **M9 packaging:** add Pumice's review checklist (§5 item 9) to the pre-submission steps, and a release-script check that the new version is strictly greater than every entry in `versions.json` (§5 item 6).
- **M3 acceptance:** add "two vaults open on one desktop, same relative path edited in both" to catch any shared per-device store (§6 item 13), and "server accepts the socket and never answers hello" to check the client's hello deadline (§5 item 13).
