# PKV Sync (CyberKurry): research report

Investigated 2026-09-22. Clones: `pkv-sync` at `2026-09-11` (v1.5.1, 584 commits since 2026-05-01) and `pkv-sync-plugin` (a release mirror of `pkv-sync/plugin/`; source and issues live in the main repo). The owner's other repos (ConvTools, video-metadata-analyzer, seedream-volcengine) are unrelated. Citations use `pkv:` for `CyberKurry/pkv-sync` and `pkv:plugin/...` for the plugin source inside it.

## 1. Summary

- **What:** self-hosted Obsidian sync, multi-user and multi-vault, with a Rust server (`pkvsyncd`) that stores each vault as a **bare git repo** (text inline as git blobs, attachments as JSON pointer files into a SHA-256 blob store), SQLite metadata, SSE live push, an admin web UI, git smart-HTTP clone, and a **built-in MCP server** (stdio, standalone HTTP, or `/mcp` embedded in `serve`).
- **Maturity:** v1.5.1, 9 stars, one issue ever filed (a Chinese user asking where the "delete vault" button is), three PRs (two Dependabot). 76k lines including tests, written in four and a half months. Strong signs of being AI-generated and AI-audited: bug IDs like `BUG-R3-01`, `SEC-R3-07`, `PERF-4`, and many "tests" that `include_str!` the source file and assert on substrings of the code (`pkv:server/src/mcp/tools.rs:2546`, `:2586`, `:2613`; `pkv:server/src/service/sync/push.rs:1082-1310`). Little evidence of real-world use.
- **License:** `AGPL-3.0-only` (`pkv:LICENSE`, `pkv:Cargo.toml` workspace `license = "AGPL-3.0-only"`), plugin mirror also AGPL-3.0. **No code may be copied into Trew (MIT).** Ideas and behaviour only.
- **Stack:** Rust (axum 0.7, sqlx/SQLite, git2 0.20 with vendored libgit2, `rmcp` 1.7 used for model types only, JSON-RPC hand-rolled), TypeScript Obsidian plugin (esbuild, vitest).
- **Verdict:** the closest competitor in shape (plaintext server, history, MCP), and a useful mirror: their MCP is **whole-file writes with a vault-wide compare-and-swap on the git HEAD**, no read scope, no idempotency, no content-trust envelope, and a vault rollback that **rewrites the branch**. Almost every place they differ from `plan/mcp-tools.md`, our plan is the more careful one, and several of their weaknesses are concrete confirmations that our decisions (per-path `base`, operation records, pins, scoped tokens, untrusted envelope) are load-bearing. Steal three or four ideas (`changes_since`, `link_graph` shape, agent change notifications with replay, git-object-liveness GC lesson, whole-vault restore as a user feature), copy nothing.

## 2. Architecture in brief

**Storage.** One bare git repo per vault under `vaults/<id>` with a single ref `refs/heads/main`. A push is one git commit built with libgit2 tree edits on top of the parent (`pkv:server/src/storage/git.rs:1031-1063`). Text files are stored as git blobs verbatim. Binary files are uploaded first to a content-addressed blob store (`<root>/blobs/<sha256>`, temp file + `sync_all` + rename, `pkv:server/src/storage/blob.rs:109-148`) and committed to git as a pointer JSON `{"pkvsync_pointer":N,"blob":"<sha256>","size":…,"mime":…}` (`pkv:server/src/storage/git.rs:30-80`). Whole-file blobs, no chunking. SQLite (`pkv:server/migrations/0001_initial.sql`) holds users, device tokens, vaults, invites, `blob_refs(blob_hash, vault_id, commit_hash)`, `sync_activity` (the audit log), `idempotency_cache`, runtime config and per-vault settings. Git and SQLite are **not** transactional with each other: the git commit lands first, then SQLite metadata is written, with a "reconcile" repair path if the second step fails (`pkv:server/src/service/sync/push.rs:444-586`).

**Sync protocol.** REST + SSE. The plugin scans the whole vault, hashes every file, pushes changed files and index-derived deletions with `If-Match: <lastSyncedCommit>` (push-first), then pulls a tree diff `since → HEAD` (`pkv:plugin/src/sync/engine.ts:239-262`, `pkv:server/src/service/sync/pull.rs:77-190`). A push against a stale HEAD whose base is an ancestor of HEAD is **auto-merged on the server** per file: three-way line merge for text, marker-bearing `.conflict-*` sidecar when the merge conflicts, remote-wins-plus-sidecar for add/add, "drop the delete" for delete-vs-modify (`pkv:server/src/service/sync/merge_apply.rs:19-448`, `pkv:server/src/service/merge.rs`). The merged result is a new linear commit on top of the current HEAD, not a merge commit. SSE events carry inline text up to 8 KiB so small edits apply without a pull (`pkv:plugin/src/sync/engine.ts:133-190`).

**History, diff, restore.** Per-file history is a revwalk from HEAD comparing each commit's tree entry against its first parent (`pkv:server/src/service/history.rs:137-193`), budgeted at 10,000 commits. Diff is `similar::TextDiff` unified diff between two commits (`pkv:server/src/service/diff.rs:39-107`). Restore is done by the **plugin**: it fetches the file at the commit and writes it into the local vault through `vault.modify`, then ordinary sync pushes it (`pkv:plugin/src/sync/restore.ts:26-66`).

**Vault rollback.** Force-moves `refs/heads/main` to the target commit (`pkv:server/src/service/vault.rs:54-151`, `pkv:server/src/storage/git.rs:498-517`), after writing a protection ref `refs/pkvsync/rollback-protected/<from>` so the abandoned commits are not garbage-collected (`pkv:server/src/storage/git.rs:475-496`). Devices receive an SSE `rollback` event and run a full sync.

**MCP.** Ten tools on the store (section 3 table below compares them with ours). Auth is an ordinary device bearer token plus a deployment-key header. Writes call the same push pipeline as devices in strict-CAS mode (no auto-merge), labelled with device name `"MCP"`, and append a `sync_activity` row after the commit.

### 3.1 Edit semantics

Theirs: every mutation is a full replacement of a path's bytes. There is no exact-edit, append or prepend primitive, no BOM handling, no noop detection (an identical `write_file` produces a new commit with an identical tree, since `commit_changes` never compares `tree_oid` with the parent tree, `pkv:server/src/storage/git.rs:1052-1058`), and no `note_too_large` beyond `max_file_size`. Ours is strictly richer and safer. Nothing to change.

### 3.2 How agent writes become versions

`apply_preflighted_write_batch` (`tools.rs:1259-1299`) calls `sync::push_with_cas` with `device_name: Some("MCP")` and `idempotency_key: None`, which runs the device push pipeline under the per-vault push lock and produces one git commit whose message is `sync: MCP\nN files changed` (`push.rs:451-456`). History attributes the change by parsing that commit message (`pkv:server/src/service/history.rs:219-226`), so **every agent is called "MCP"** regardless of which token wrote; the token id is only in the `sync_activity` row. Our plan's per-token author label on the version row is better.

### 3.3 Agent write versus device write

The precondition is **vault-wide**: `parent_commit` must equal the current HEAD exactly (`tools.rs:1236-1257`, re-checked under the push lock in `push.rs:241-285`, and again by libgit2's `repo.commit(Some(MAIN_REF), …, &[parent])`, which refuses when the ref's tip is not the first parent). MCP writes use `StalePushMode::StrictCas`, so they never auto-merge (`push.rs:126-149`). Consequences:

- Any device commit to any file invalidates the agent's precondition. On an actively edited vault an agent's write is refused far more often than necessary, and each refusal burns the 60/min write quota because the rate limit is recorded **before** the CAS check (`tools.rs:1208-1216`).
- The conflict reply is `{conflict: true, current_head}`. The obvious agent response is "retry with `parent_commit = current_head`", which **silently overwrites a device edit to the same file** because the agent's content was computed from an older read. The server cannot tell "retried after re-reading" from "retried blindly". A per-path `base` (ours) makes the stale signal specific to the path the agent read, so a blind retry is refused whenever it matters and allowed whenever it does not.
- Devices, conversely, *do* auto-merge against agent commits: a phone that pushes a stale edit gets a server-side three-way merge with the agent's version, or a `.conflict-*` sidecar. That is roughly what PLAN §4.6 gets for free from the phone's own engine.

### 3.4 MCP auth

A normal device token (`pks_…`, 90 days idle, 365 absolute, `pkv:README.md` "Obsidian plugin") plus the global deployment key header. **No scopes**: the MCP doc states "A bearer token gives read and write access to every vault owned by that user" (`pkv:public-docs/mcp-howto.md`, "Streamable HTTP transport"). Revocation is checked per request through an epoch-invalidated 5-second cache (`pkv:server/src/mcp/auth.rs:18-76`), which is a reasonable pattern. Rate limits: 120 requests/60 s per client IP (not per token) on HTTP, 30 failed auths/60 s, 60 writes/min per (token, vault). No `Origin` check; the custom deployment-key header forces a CORS preflight, which in practice blocks browser-driven DNS-rebinding requests. Our plan (dedicated MCP tokens, `read` default, scope checked three times, per-token budgets, `Origin` allowlist) is stronger on every axis.

### 3.5 Audit and undo

Audit: a `sync_activity` row `mcp_write`/`mcp_delete` with `{path, commit, size_bytes}` (for batches `path` is `"N files"`), written **after** the git commit and outside any transaction with it (`tools.rs:1305-1339`). If that insert fails, the tool returns an error to the agent even though the commit landed: exactly the "committed ≠ known" case PLAN §4.8 calls out, with no idempotency key to recover it. Undo: none. The doc's answer is "roll back with normal git operations" (`mcp-howto.md`, "Caveat: writes enter git history"), which in practice means the whole-vault rollback in §2, discarding every device edit made after the agent's commit.

## 5. Ideas worth adopting

1. **`changes_since` tool.** `{afterUid, folder?, limit, cursor}` → `[{path, kind, uid, previousUid, previousPath?, deleted}]`, `nextCursor`, `complete`, `head`. An agent that maintains a wiki or a digest keeps a checkpoint UID and asks "what changed since I last looked". With a monotonic UID log this is one indexed range scan, never an ancestry question, and it survives a vault restore (unlike theirs, which returns `unrelated_commit` after a rollback). Land in `plan/mcp-tools.md` read tools and M4.
2. **Vault health in one call.** Their `link_graph` returns orphans and broken links with a `missing`/`ambiguous` reason, plus `truncated`. Promote `plan/ideas.md` "Backlinks and vault health" into M4 or M5 as `vault_links {folder?, limit, cursor}` built on `note_links`. Test cases worth borrowing by name: links relative to the source directory, `../` links that escape the vault root must not fall back to a basename match (`tools.rs:2040`), ambiguous basename links, non-UTF-8 targets ignored, hidden paths never reported even when allowlisted (`tools.rs:1860`).
3. **Agent change notifications with honest replay.** Replay from `Last-Event-ID` when possible, emit an explicit `lagged` when the gap cannot be covered, never silently skip (`pkv:CHANGELOG.md` "replay before-subscribe race and multi-vault reconnect gaps"). If we add it, use standard MCP resource subscriptions. Land in `plan/ideas.md` next to webhooks; the lagged rule belongs in whatever event stream we build.
4. **Whole-vault restore as a user-visible feature, done as a compensating operation.** Their "rollback vault to here" in the history panel (`pkv:plugin/src/ui/history-modal.ts:213-222`, typed vault-name confirmation) shows users want it. Ours should be `restore_vault {toUid}` (admin/control socket and plugin, not MCP by default): compute every path whose head differs from its state at `toUid`, append one operation of versions restoring those states (including tombstones for paths created since), pin every displaced head, record it in `operations` so it can itself be undone. No history rewrite, devices see ordinary remote changes, and `changes_since`, cursors and preconditions stay valid. Land in PLAN §4.5 (undo) as a follow-on and in `plan/ideas.md`.
5. **Blob liveness must follow history reachability, not HEAD.** Their BUG-R3-01: reconcile deleted `blob_refs` for blobs no longer in the HEAD tree, so after the 7-day GC grace, attachment content in history was permanently lost and restore/rollback silently broke (`pkv:CHANGELOG.md` 1.5.0 "Vault metadata reconcile no longer deletes `blob_refs` rows…"). PLAN §4.5 already says "chunk reclamation considers every surviving reference"; add a test that names this failure: purge, then restore an attachment version that is not a head, and verify its bytes.
6. **Abandoned uploads need an expiry.** Their BUG-R3-14: blobs uploaded but never committed were protected forever, filling the disk. Basalt's purge handles orphan chunks; confirm the Trew purge reclaims chunks stored by a failed or abandoned MCP operation (PLAN §4.3 step 3 stores bodies before the commit, so an operation that then fails `stale` leaves orphans by design).
7. **Refuse, do not truncate, when a scan bound is hit.** Their `search` fails outright above 5,000 files rather than returning a partial answer that looks complete. We already have `complete: false`; keep the rule that a bound is never silent, and consider refusing with `scan_incomplete` when the caller asked for exhaustive results.
8. **Read-only `git clone` of the vault** is a genuinely nice interoperability feature for a plaintext server (`pkv:public-docs/git-clone-howto.md`, upload-pack only, `pkv:server/src/api/git_http.rs:54`). Our equivalent is `serve --export-dir` in `plan/ideas.md`; note git export as an alternative output format there, not a storage model.

## 6. Their bugs or weaknesses we must not repeat

1. **Read returns no version, so the documented agent loop can lose updates.** `read_file` returns content without the commit it was read at (`tools.rs:82-88`); the head comes from `list_vaults`. An agent that reads a file, then fetches the head for `parent_commit`, can pick up a head that already contains a device's edit to that file and overwrite it without a conflict. The only safe sequence (`list_vaults` → `read_file_at_commit(head)` → write) is not documented; the LLM-wiki guide says "use `parent_commit` from the last read" (`pkv:public-docs/llm-wiki-howto.md`, "Connect an agent"), which the read tool cannot supply. Our `read_note` returns `uid` and `head`; add a contract test that the `uid` in the read result is the one the content came from, under a concurrent commit.
2. **Vault-wide CAS plus a reply that invites blind retry** (§3.3). Keep per-path `base`, and make `stale` carry `currentUid` for that path only, never a vault-level token an agent can paste back.
3. **Audit written after the commit and able to fail the reply** (`tools.rs:1286-1293`). PLAN §4.3 step 5 already puts the `operations` row in the commit transaction; keep it there, and add a test where the audit insert is forced to fail and the whole operation rolls back.
4. **No idempotency on MCP writes** although the REST push has it (`idempotency_key: None` in `push_with_cas`, `push.rs:140`). PLAN §4.8 is right to require it.
5. **Rate limit consumed before the precondition check** (`tools.rs:1208-1216`): refused writes cost quota, which under the vault-wide CAS makes an agent on a busy vault rate-limit itself. Charge budgets for work done, and let `stale` be cheap.
6. **Git writes are never fsynced.** libgit2 defaults to no fsync for objects and refs, and the code never enables it (the only `sync_all` in the server is in `blob.rs:139`, and even that does not fsync the directory after rename). A push is acknowledged after `repo.commit` returns, so a power loss can lose an acknowledged commit or leave `refs/heads/main` pointing at a truncated loose object. This violates durability rule 1 at the storage layer. Basalt's store already does this right; do not relax it in any "simplification".
7. **Two stores, no shared transaction.** Git commit first, SQLite metadata (blob refs, idempotency, stats, activity) second, repaired by a reconcile pass on failure (`push.rs:521-575`). It works because git is the source of truth, but it is why they accumulated BUG-R3-01 and a string of idempotency fixes. Our single SQLite transaction for entries, operations, pins and idempotency is the thing to protect.
8. **Rollback rewrites history.** Force-moving `main` (`git.rs:498-517`) means: per-file history, which walks from HEAD (`history.rs:150`), no longer shows the undone versions; `changes_since` checkpoints before the rollback become `unrelated_commit`; rollback targets older than 10,000 commits are refused (`MAX_REACHABLE_WALK`, `git.rs:15`) unless protected; and every device's local edits made after the target are either conflict-copied or silently replaced depending on whether they were pushed. It needed a protection-ref mechanism and "Rollback history is protected from concurrent overwrites during rapid push retries" (`CHANGELOG.md:371`) to avoid losing the undone commits entirely. An append-only compensating restore (§5.4) has none of these problems.
9. **The plugin rehashes the entire vault on every sync.** `scan` reads and SHA-256s every file each pass, with no mtime/size shortcut (`pkv:plugin/src/sync/vault-adapter.ts:113-143`), and sync runs on a debounce after each edit, on window blur, on a poll timer and on a fallback timer (`pkv:plugin/src/sync-orchestrator.ts:66-81`, `:120-125`). On a phone with a large vault that is a battery and latency problem. Basalt's index journal avoids it; keep it.
10. **No mass-deletion guard.** Deletions are "paths in the index that the scan did not see" (`engine.ts:217-219`) and are pushed first, before any pull. A scan that returns too few files (vault not fully loaded, sync started from `onload` rather than `onLayoutReady`, `pkv:plugin/src/main.ts:156`) becomes a vault-wide delete commit. There is no threshold or confirmation anywhere in `plugin/src/sync`. Durability rule 2 exists for this; Basalt's engine already refuses to treat a failed or empty read as a deletion.
11. **The inline-apply TOCTOU was narrowed, not closed.** The "fix" re-reads and re-hashes before `vault.modify` (`engine.ts:639-667`, `CHANGELOG.md:274-277`), but an editor keystroke between the second hash and the write is still clobbered. `vault.process` (or Basalt's preserving replace) is the actual fix. Also note conflict copies are named to the second with no nonce on the client (`pkv:plugin/src/sync/conflict.ts:14-32`), so two conflicts on one file in one second overwrite the first copy via `vault.modify`. The server-side sidecar name has a nonce (`merge_apply.rs:528-562`); the client's does not.
12. **Likely non-functional `.obsidian` allowlist.** `listFiles` finds config files by `vault.getAbstractFileByPath(".obsidian")` and walking its `TFolder` children (`vault-adapter.ts:32-44`), then reads them with `vault.read(TFile)`. Obsidian does not put the config directory in the vault's file tree, so in real Obsidian that lookup returns `null` and nothing under `.obsidian` is ever seen. The only test builds a mock tree that contains a `.obsidian` `TFolder` (`pkv:plugin/tests/sync/vault-adapter.test.ts:119-138`). Config files need `vault.adapter.list/read/write`. This is an example of the pattern to avoid: a feature "verified" only against a mock of the platform. Our §4.1 refusal of dot-segments sidesteps it, but the headless and plugin adapters should have one integration test against a real Obsidian vault layout.
13. **No rename handling.** No `vault.on("rename")` listener (`sync-orchestrator.ts:120-122`) and no rename in the wire model: a rename is a delete plus a create, a folder rename is N of each, and history does not follow the file. Basalt's `prev`/`prevBase` rename entries are better.
14. **Smaller MCP defects.** `changes_since` `path_prefix` is a raw `starts_with` (`tools.rs:599`), so `wiki` matches `wikipedia/…`; search folds ASCII only (`tools.rs:347`); search returns whole lines unclipped; `move_file` refuses non-UTF-8 and binary sources outright; the HTTP rate limit is keyed on client IP, so two agents behind one proxy share a bucket and one noisy token starves the others.
15. **Plugin self-updates its own `main.js`** from the server or GitHub (`pkv:plugin/src/services/update-check.ts`), which the Obsidian community plugin guidelines disallow and which makes the sync server a code-delivery channel into every device. Do not add this to the Trew plugin.

## 7. Where they contradict our plan, and who is right

| Topic | PKV Sync | Trew plan | Verdict |
|---|---|---|---|
| Storage model | Bare git repo per vault, whole-file blobs, SQLite beside it | SQLite version log + content-defined chunks (PLAN §2.2) | **Ours** for this product. Git gives free `clone`, diff and a familiar mental model, but costs fsync control, cross-store transactions, a global HEAD that serialises every writer, `git gc` shelled out to a `git` binary under the push lock (`pkv:server/src/service/cleanup.rs:133-196`), and whole-file attachment storage. Per-path UIDs are what make per-path preconditions possible. |
| Precondition granularity | Vault HEAD | Per-path version UID | **Ours** (§3.3, §6.2). |
| Whole-file MCP writes | `write_file` is the only writer | Refused for v1 (PLAN §4.4) | **Ours.** Their design is the counterexample §4.4 describes. |
| Server-side auto-merge of stale device pushes | Yes, three-way on the server | No; the device engine merges (PLAN §2.6, §4.6) | **Ours** for Trew, because the Basalt engine already merges with validity gates and preserving writes, and a second merge implementation on the server is the "two engines" hazard §2.6 refuses. Their server merge also cannot see the device's unsynced edits and turns a delete-vs-modify into a silently dropped delete reported only in a `merge_outcomes` array. |
| MCP credential | Device token, all vaults, read+write | Separate MCP tokens, `read` default, scoped, labelled | **Ours.** |
| Agent identity in history | Literal `"MCP"` in the commit message | Token label as author row | **Ours.** |
| Retention | Keep all git history forever; prune only unreachable objects after two weeks | Purge with heads, rename chain and operation pins (PLAN §4.5) | Theirs is simpler and never loses a before-image, at the cost of unbounded growth. Ours is right to allow purge but must keep the pins. Worth stating in `docs/` that default purge settings keep before-images for at least the pin window. |
| Vault rollback | History rewrite with protection refs | Not in plan; undo is per operation | **Ours** in principle, but they have a feature we lack. Add it as a compensating operation (§5.4). |
| Content trust | None: note text returned raw in `content` and `line` | Structural `trusted` / `untrusted_content` envelope (PLAN §4.10) | **Ours.** A writing agent with no content boundary is the worst case §4.10 describes. |
| Multi-user, multi-vault, admin web UI | Yes | Refused (PLAN §1 scope) | Different products. Nothing here argues for widening our scope. |
| Sync-path filter as MCP visibility | Excluded and hidden paths are invisible to MCP; writes use a stricter policy than reads (`tools.rs:621-623`) | Server path policy refuses dot-segments at `put` (PLAN §4.1) | Compatible. Their split (reads may see allowlisted hidden paths, writes never address them) is a sensible rule if we ever allow any dot-path. |
