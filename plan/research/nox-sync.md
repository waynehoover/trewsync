# NoX Sync (mapherez/nox-sync): code investigation

Checked out at `c625299` (2026-09-16), 116 commits, cloned to the session scratchpad. Repo refs are `nox:path:line`. Our refs are `basalt:path:line` (commit `664a963`) or `PLAN.md §x`.

## 1. Summary

- **What:** a manual, user-triggered Obsidian sync. A Go backend (HTTP+JSON, SSE for lock status only, SQLite, whole-file blobs named by SHA-256) and a single-file TypeScript plugin. Each sync takes a per-vault lock, sends a whole-vault manifest, gets back a plan, runs it, then commits.
- **Maturity:** young, probably generated by an agent from a spec. The specs (`SPECS/1-project-description.md`, `2-official-stack.md`, `3-implementation-milestones.md`, deleted in `0504e35`) were written on 2026-05-13, "milestones 0 to 8" were all committed within 26 hours, and multi-user plus Google OAuth arrived a day later. Since then the history is mostly dependabot. It has 1 star, no issues, and one non-bot PR. About 2,000 lines of Go, 2,826 lines of plugin in one `main.ts`, 25 Go tests and 1 small TS test file.
- **License:** **GPL-3.0** (`nox:LICENSE`, and `"license": "GPL-3.0-only"` in `nox:plugin/package.json`). **We can take ideas only and must not copy any code.**
- **Stack:** Go 1.27, `net/http`, `modernc.org/sqlite`, Google OAuth for the dashboard, one `noxsync_` API key per user (the plaintext key is also stored so the dashboard can show it again). The plugin uses `requestUrl`, `EventSource` and `vault.readBinary`/`createBinary`/`rename`, with no framework.
- **Verdict:** there is nothing to reuse. Its value is as a worked example of what a manifest-diff, lock-and-commit design gets wrong. I reproduced two data-integrity defects with Go tests against their store (§6.1, §6.2). They also contain one idea worth keeping for our one-shot and headless peer: plan first, then apply.

## 2. Architecture in brief

**Why manual.** The spec gives preference, not engineering, as the reason: "Manual sync only. No automatic file download or automatic file application when Obsidian opens ... No sync without explicit user action" (deleted `SPECS/1-project-description.md` §3, §11). The product goal is predictability ("the button clearly tells me whether there are local changes, remote changes ... The system never silently overwrites my data", §35). On startup the plugin may check server status but must never touch files (`nox:plugin/src/main.ts:238-269`). Manual sync is what the user sees. It is not a durability argument, and the implementation does not get any durability from it.

**Session protocol** (`nox:backend/internal/storage/sync.go`):
1. `POST /v1/sync/begin`: in one transaction, take the per-vault row in `sync_locks` (TTL 2 minutes, heartbeat every 10 s, `sync.go:15-16`, `:49-154`). A lock past its expiry is stolen, and the old session is marked failed.
2. `POST /v1/sync/manifest`: the client sends every file as `{path, hash, size, lastKnownRevision}`, plus `deletedPaths` and a vault-wide `lastKnownServerRevision`. The server compares this with the `files` table and stores a plan in `sync_plan_actions`. Actions are `upload`, `download`, `delete_remote`, `delete_local`, `conflict` and `none` (`sync.go:185-335`).
3. `PUT /v1/sync/upload/{session}?path&hash&size`: the whole file goes to `staging/<session>/<hash>`, is hashed on the way in, and is refused on a mismatch (`nox:backend/internal/storage/blob.go:17-99`).
4. The client downloads through `GET /v1/files/download` (not tied to the session). Before replacing or deleting a file it re-checks that the local file still matches the manifest hash, moves the old file to `.nox-sync-trash/<timestamp>/<path>`, then calls `createBinary` (`main.ts:936-972`).
5. `POST /v1/sync/commit`: this is refused if any action is `conflict`. Otherwise staged files are copied into `blobs/`, and one transaction rewrites `files` rows (current hash and **one** previous hash), appends `file_revisions`, bumps the vault revision by one and releases the lock (`sync.go:338-447`).

**Change detection.** Local changes are found by a full re-read and re-hash of every file from `vault.getFiles()` (`main.ts:1759-1814`). This scan runs 1.5 s after any `create`/`modify`/`delete`/`rename` event (`main.ts:1859-1865`), at startup, and before every sync. There is no stat cache. Remote changes are detected only by comparing the vault's integer revision with the one last seen (`main.ts:1740-1753`).

**Deletes.** Deletes are explicit (`knownFileHashes` minus the paths seen) and are also **inferred from absence on the server** (§6.2). There is a `tombstones` table, but the planner never reads it. It uses `files.deleted` instead.

**Renames** are not a concept at all. The `rename` handler records a delete of the old path and a change at the new one (`main.ts:1854-1857`). A rename therefore costs a full re-upload of the bytes (blob dedup saves disk only), and a rename racing an edit elsewhere becomes a delete/modify conflict on the old path.

**Conflicts.** A file conflicts when `local.hash != remote.current` and the local hash does not equal the server's single `previous_hash` (`sync.go:243-261`). Any conflict stops the whole sync before anything runs (`main.ts:780-784`). The user then resolves each file in a modal (keep local, keep remote, keep both, or edit a textarea) and presses sync again. `base_hash` exists in the schema, but the server never fills it (`grep BaseHash` finds only reads), so no three-way merge is possible.

**History** is a row in `file_revisions`. It has no reader, no restore endpoint and no UI (every dashboard route is in `nox:backend/internal/app/server.go:35-62`). Because `blobHashReferenced` counts `file_revisions` (`nox:backend/internal/storage/vaults.go:397-420`), those blobs are also never reclaimed except by purging the whole vault.

## 4. Ideas worth adopting

1. **A plan-then-apply mode for the headless client** (`trew-sync sync --dry-run`, or a `plan` subcommand). NoX's real good idea is making the diff an inspectable object before anything changes (`sync.go:185-335`). For a one-shot NAS or agent peer run from cron, and for the M10 cutover, printing "would upload N, download M, delete K (to trash), conflict J" and exiting 0 or 1 without writing is cheap and very useful. Basalt's CLI has no dry-run (`basalt:client/src/cli/usage.ts` lists no such flag). **Lands in:** PLAN.md §2.7 (headless client is production code), as an M2 task, and in M10 as a verification step before enabling the new writer.
2. **"Remote has changes" without applying them.** NoX uses `serverRevision > lastKnownServerRevision` to light a REMOTE_DIRTY state with no download (`main.ts:1740-1753`). For our one-shot peer, `trew-sync status` could report "server head is ahead of my cursor by N versions, K local changes unpushed" from a single `hello`/cursor exchange. That lets a scheduler decide whether a full pass is worth running. **Lands in:** PLAN.md §4.9, where `trew-sync status` already exists; add these two fields.
3. **Hash equality as the convergence check makes a lost commit reply harmless.** If a NoX commit succeeds and the reply is lost, the client keeps its old state. On the next pass every path hashes equal to the remote head and plans `none` (`sync.go:239-240`, `:277-279`). This is the one property of their design that is truly robust, and our one-shot peer must have it too: killed after the server commits but before the index journal records it, the rerun must converge with **no conflict copy and no duplicate version**. **Lands in:** PLAN.md §4.8 ("committed is not known") and the M2/M3 test gate for the headless client, as a named crash case.
4. **The status stream is for locks and presence, not content.** Their SSE carries only lock state (`nox:backend/internal/app/status_broker.go`). We have no lock, but the same shape (a cheap push saying "head moved to N", no content) is what a mostly-offline headless peer or a webhook consumer needs. **Lands in:** plan/ideas.md "Webhooks or an event stream". It supports putting head-moved events there, and nothing more.

## 5. Gotchas and platform quirks they discovered

1. **`vault.createFolder` throws "folder already exists" for a folder the vault index does not show.** They fixed it by catching the message string (`nox:plugin/src/sync-core.ts:206-219`, commit `0f465a4` "fixed 'folder already exists' error"). It happened while creating `.nox-sync-trash/...`. That is a dot-folder, which Obsidian does not index, so `getAbstractFileByPath` returns null and the create then collides with the real directory on disk. **Lesson for us:** index lookups lie about dot-paths. Basalt's adapter layer should keep using `adapter.exists` for anything under a dot-folder (our `.trew` state and staging dirs).
2. **`vault.getFiles()` never returns dot-files, so their "Sync hidden files" toggle does nothing.** `shouldExcludePath` checks `syncHiddenFiles` (`main.ts:1887`), but the manifest is built only from `getFiles()` (`main.ts:1763`), which leaves those paths out whatever the toggle says. The setting is shown to users and does nothing. This backs our §4.1 decision to refuse dot-segments outright rather than offer a toggle.
3. **Obsidian 1.13 declarative settings.** Their last feature commit (`e2bed0e`, 2026-08-07) moved to `PluginSettingTab.getSettingDefinitions()` returning `SettingDefinitionItem[]` with `aliases`, `searchable` and `visible` (`main.ts:2305`, types hand-declared in `nox:plugin/src/obsidian-shim.d.ts:129-144`), and raised `minAppVersion` to 1.13.0. This is a platform fact worth knowing for the plugin's settings panel: new API, searchable settings. Adopting it means raising our `minAppVersion`, so decide deliberately.
4. **An empty folder left behind after a remote delete** was a real complaint they fixed (`eae0607`) by pruning empty parents deepest-first with `fileManager.trashFile` (`main.ts:1616-1635`). Basalt syncs folders as entries, so it does not have this problem, but it confirms users notice.
5. **`EventSource` cannot send headers,** so they put the API key in the query string (`main.ts:1898-1903`, accepted by `nox:backend/internal/app/server.go:384-391`). The backend sends no CORS headers (a grep for `Access-Control` in `backend/` finds nothing), and Obsidian desktop and mobile pages run on non-http origins (`app://obsidian.md`, `capacitor://localhost`). So this stream very likely never connects inside Obsidian, and `onerror` falls back to calling `/v1/status` and reconnecting every 5 s forever (`main.ts:1913-1917`). I did not run this in Obsidian, so it is inferred. **Lesson:** anything the plugin opens outside `requestUrl` is subject to CORS. Basalt's WebSocket is not (WebSocket is not CORS-gated), which is another quiet reason to keep it.
6. **Private API:** `this.app.setting.open()` / `openTabById` (`main.ts:808-809`). This is common and has worked for years, but it is undocumented.

## 6. Their bugs or weaknesses we must not repeat

1. **A file changed twice elsewhere shows up as a conflict on a device that never touched it.** The planner keeps only one `previous_hash` per path and never gets the client's base hash. The client keeps `knownFileHashes` but sends only the current hash and a revision (`main.ts:83-89`, `sync.go:243-261`). **Reproduced:** A commits v1 (rev 1), B commits v2 (rev 2), then v3 (rev 3). A is unchanged at v1 and syncs. The plan is `conflict` instead of `download`. Under manual sync this is the *common* case (a phone synced weekly), and any conflict blocks the whole sync (`main.ts:780-784`). If the user answers "keep local", B's two edits are overwritten by the stale copy. **Our rule:** the precondition is the base the client last saw (Basalt's `base`/`prevBase`, protocol.md). It is never the server's idea of "the previous version". Add a stress case: a peer offline across two or more remote versions of a path it left unchanged must fast-forward.
2. **The server treats a missing file as a delete.** If a remote file is absent from both `files` and `deletedPaths`, and the file's revision is at or below the client's `lastKnownServerRevision`, the planner emits `delete_remote` (`sync.go:299-318`). **Reproduced:** a manifest with zero files and no `deletedPaths`, sent with `lastKnownServerRevision=1`, deletes `keep.md` on commit. After that, `DownloadFile` returns not found. Anything that shrinks the manifest without meaning to (a filter, a case-folding filesystem showing one of `Note.md`/`note.md`, a scan that returns early, a mount that is not there yet) becomes real deletes. This breaks our durability rule 6 ("Deletions are entries, not absences") and rule 2. It is exactly the hazard a headless NAS peer faces when its share or disk is not mounted.
3. **The manifest is capped at 1 MiB,** because every JSON body is capped (`nox:backend/internal/app/sync_handlers.go:15`, `:224`), and the manifest lists every file with a 64-character hash. At about 120 bytes per entry, a vault of roughly 8,000 to 9,000 files cannot sync at all, and the error says "Request body must be valid JSON." Upload bodies, on the other hand, have no cap at all (`blob.go:58`). **Lesson:** do not send a whole-vault manifest on the hot path. Basalt's cursor-based catch-up plus per-path entries is the right shape, and every bound needs a clear error.
4. **A crash can leave a truncated blob that is trusted forever.** `ensureBlob` returns early if the final blob path exists (`blob.go:107-109`). `copyFile` writes straight to that final path with no temp-and-rename, and syncs the file but not the directory (`blob.go:125-154`). A crash mid-copy leaves a short file under the correct hash name, and the next commit that needs that hash trusts it. The staging file is renamed without an fsync (`blob.go:79`). Basalt's `chunks.Writer` + `Close()` (fsync) and `internal/fsync` directory sync are the right pattern (PLAN.md §4.3 step 3). Keep verifying the hash on read (PLAN.md §2.2), because the name alone proves nothing after a crash.
5. **Garbage collection races uploads.** When a vault is purged, blobs are deleted after the transaction whenever no row references them (`vaults.go:239-277`, `:383-395`). Blobs are global across users and vaults (`nox:backend/internal/storage/path.go:41-47`). A concurrent session that has already passed `ensureBlob`'s existence check (`blob.go:108`) commits a reference to a blob the purge then removes. Purge must hold the commit lock and count in-flight staging. Basalt's purge under `commitMu` and the survivor-set design (PLAN.md §4.5) is the right model. Global cross-user dedup is also a presence oracle, which PLAN.md §2.2 already rules out by scoping to the vault.
6. **Replacing a file renames the open file into a hidden trash folder.** Downloads and "keep remote" call `vault.rename(file, ".nox-sync-trash/...")` and then `createBinary` (`main.ts:1610-1614`, `:950`, `:1327-1335`). An open editor follows its `TFile` on rename, so the user's tab may now point into an unindexed dot-folder the sync ignores, and further typing lands there. This is inferred from how Obsidian renames work, not run. The rename also fires their own `rename` handler, which queues the path as a pending delete mid-sync (`main.ts:1854-1857`). It is cleared only by a successful commit. This is precisely the failure Basalt's preserving-write adapter (`vault.process`/`modify` on the existing `TFile`) exists to avoid. **Do not accept any proposal to simplify the plugin adapter to delete-and-create.**
7. **Every file is re-read and re-hashed on every debounce** (`main.ts:1759-1814`, triggered 1.5 s after any vault event). On a large vault on a phone, typing causes whole-vault reads. The per-file state (`knownFileHashes`, `knownFileRevisions` for the entire vault) lives in `data.json` and is rewritten on each delete event (`main.ts:1837-1852`). Basalt's index journal with a size/mtime check (`basalt:client/src/core/index-journal-store.ts:510`) is the right design. The headless one-shot peer must persist and use it across runs, or every cron pass is a full-vault read.
8. **The commit re-checks the lock outside its transaction.** `ensureActiveSession` runs before `BeginTx` (`sync.go:339`, `:381`), and `releaseLockTx` ignores `RowsAffected` (`sync.go:976-985`). The commit does not re-validate planned revisions and relies on the lock alone. The window is milliseconds, but it is the same check-then-commit gap PLAN.md §2.3.1 calls out. Recheck under the commit boundary (PLAN.md §4.3 step 4).
9. **"Current plus previous version" is promised and never delivered.** There is no restore path anywhere (routes listed at `server.go:35-62`), and the `file_revisions` rows are write-only. This is our rule 11 ("a recovery path tested only in docs is a rumour") in a pure form. The trash folder is the only real recovery, it lives on the device only, and the user can empty it with one button (`main.ts:1395-1407`).
10. **Credential handling.** The API key is stored in plaintext beside its hash so the dashboard can show it again (`nox:backend/internal/storage/migrations/003_multi_user_multi_vault_reset.sql` `api_keys.key_value`, `api_key.go:27`). It is shared across all of a user's devices, so revoking one device is impossible. It also travels in a URL query string (§5.5), which ends up in proxy logs. PLAN.md §2.3 (per-device tokens stored hashed, shown once) is right on every point.
11. **The path policy is weak.** `NormalizeVaultPath` (`path.go:14-32`) does `path.Clean` and checks for traversal, and nothing else: no NFC, no control characters, no case-alias detection, and dot-segments are allowed. Two devices with NFC and NFD forms of one name produce two server paths. PLAN.md §4.1 already covers all of this.

## 7. Where they contradict our plan, and who is right

| Their choice | Our plan | Who is right |
|---|---|---|
| Manual sync only, as a product principle | Live WebSocket sync with fan-out (PLAN.md §1, §3.2) | **We are**, for devices. Manual sync gave them no durability; the risky cases (long gaps, many remote versions) get *more* common. Manual sync is still a legitimate **mode**: our one-shot `trew-sync sync` (Basalt already has it, `basalt:client/src/cli/client-options.ts:33-36`) is the same UX with our engine behind it. Offer "sync when I say so" as a plugin setting later if anyone asks. Do not make it a separate algorithm. |
| One sync session per vault, enforced by a server lock with a 2-minute TTL | Concurrent sessions, conditional writes per entry (`base`/`prevBase`/`stale`) | **We are.** A lock serialises devices, blocks everyone for up to 2 minutes when a phone is backgrounded mid-sync, and still does not make their planner correct (§6.1, §6.8). Per-entry preconditions are finer-grained and survive a stolen lock. It also matters for MCP: an agent write could never wait on a device's session lock. |
| The server computes the plan from a full manifest | The client engine reconciles from a cursor and per-path versions; the server is a versioned store | **We are.** A full manifest is O(vault) per sync, hits the 1 MiB cap (§6.3), and turns absence into deletion (§6.2). |
| One previous version per path | Full version history with retention by reference (PLAN.md §4.5) | **We are.** One previous hash causes both the false conflicts (§6.1) and the fact that history is useless. |
| Any conflict blocks the entire sync until resolved in a modal | Merge where it is safe; otherwise keep both as a conflict copy and keep syncing everything else (PLAN.md §4.6) | **We are**, especially for unattended peers and MCP, where nobody is there to click the modal. Their "never resolve silently" instinct is sound, and Basalt meets it with conflict copies and history rather than a blocking UI. |
| Replaced local files go to a device-local trash folder | Replaced content is a version on the server; the plugin writes in place | **We are**, but the trash gives one real benefit: a copy on the device survives even a server loss. We already have server history, and PLAN.md §2.8 already says to back up readable local notes separately. There is nothing to change. |
| Whole-file blobs, no chunking | Content-defined chunks (PLAN.md §2.2) | **We are** for attachments and renames. Their renames re-upload every byte. |
| Multi-user, multi-vault, Google OAuth dashboard | One person, one vault, no web UI, no OAuth (PLAN.md §1 scope) | Different products. Nothing here argues for widening our scope. Their `003` migration **drops every table** to add multi-user (`003_multi_user_multi_vault_reset.sql:1-14`), a destructive schema change shipped four days after release. It is a reminder of why PLAN.md §2.8 insists on a product id, schema version and epoch, with refusal instead of reset. |

## 8. Concrete recommended changes to PLAN.md

- **§2.7 / M2:** add `trew-sync sync --dry-run` (or `trew-sync plan`). It prints the per-path actions the engine would take (upload, download, delete, merge, conflict copy), writes nothing to disk or server, and exits nonzero if the pass would create a conflict copy or delete more than a threshold. Test: run the dry-run, then a real pass, and check that the real pass performs exactly the planned actions on an unchanged vault.
- **§2.7 / M2 (headless safety):** add a **vanished-root and mass-delete guard** to the headless client. If the vault directory is missing, not a directory, or empty while the index journal lists live files, or if one pass would delete more than N% or N files, refuse unless `--allow-mass-delete` is given. This is the NAS failure NoX would turn into real deletes (§6.2). I did not find an existing guard in Basalt's CLI. Confirm before adding, and cite it if one exists.
- **§4.8 / M3 crash matrix:** add a named case: "one-shot headless peer killed after the server commits its batch and before the local index journal records it; rerun converges with zero conflict copies and zero extra versions." This is NoX's one robust property (§4.3) and it should be ours, proven by a test.
- **§4.6 / M5 stress:** add "peer offline across two or more remote versions of a path it left unchanged fast-forwards without a conflict copy." NoX fails exactly this (§6.1). Basalt should pass it, and the test pins it for the strip-down.
- **§4.9:** extend `trew-sync status` with `behind: <versions>` (server head minus the cursor, from one handshake with no downloads) and `unpushed: <paths>`, so a scheduler can skip passes with nothing to do.
- **§3.3 / M1:** write down that a chunk is written to a temp name, fsynced, renamed, and its directory fsynced, and that the store never treats "exists at the hash name" as "valid". Either verify the hash when adopting an existing file or rely only on writer-committed metadata rows. NoX's `ensureBlob` shows the failure (§6.4).
- **§4.5 (purge):** state that purge runs under the same commit boundary as appends and treats in-flight uploads (chunks stored but not yet referenced by an entry) as survivors for a grace window. NoX's post-commit blob deletion races concurrent sessions (§6.5).
- **§2.3:** add one sentence: no credential ever goes in a URL query string, including for any future SSE or event stream (plan/ideas.md webhooks/SSE). Use a header, or a short-lived single-use ticket.
- **§4.1:** no change needed. NoX's hidden-files toggle is a no-op (§5.2), which supports refusing dot-segments outright rather than making it configurable.
- **Plugin adapter (reuse-map, M2):** add a line saying the preserving-write adapter is load-bearing and must not be "simplified" into rename-aside plus create. Cite NoX §6.6 as the counterexample.
