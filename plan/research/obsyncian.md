# Obsyncian (Syncian): code investigation

Investigated 2026-09-22 at `aabulkhairov/obsyncian` HEAD `411781c` (plugin 1.0.18), cloned to the session scratchpad. References of the form `obsyncian:src/sync.ts:305` point into that checkout. `eslint:` points into `obsidianmd/eslint-plugin` at `d7e2239` (2026-08-24), the rule set behind the community directory's automated review.

## 1. Summary

- **What:** the client plugin of a commercial hosted E2EE sync service (Rails API, closed; blobs in Cloudflare R2 via presigned URLs). Display name "Syncian", id `obsyncian`, listed in the new community directory at community.obsidian.md.
- **Maturity:** young and small. 32 commits between 2026-07-02 and 2026-09-18, about 2,500 lines of source and 1,300 of tests, one maintainer, one GitHub issue ("payment portal is in TESTMODE"). Several commits are co-authored by Claude. Commit messages are careful and honest; the sync model underneath them is naive.
- **License:** MIT, "Copyright (c) 2026 Almas Abulkhairov" (`obsyncian:LICENSE`). Code reuse is allowed with the notice kept.
- **Stack:** TypeScript, esbuild, vitest, one runtime dependency (`node-diff3`). WebCrypto only. HTTP polling of a revision-cursor change feed; whole-file blobs; per-file optimistic concurrency on a random `file_id`.
- **Verdict:** nothing in the sync engine is worth copying; Basalt is several generations ahead on every axis it touches. The value is (a) a documented, recent pass through the community directory's automated review, which Trew will face and Basalt has never faced, and (b) a clean catalogue of the failure shapes a whole-file, cursor-plus-UUID design produces, most of which our durability rules already forbid.

## 2. Architecture in brief

**Server contract** (inferred from `obsyncian:src/api.ts`): `GET /v1/vaults/:id/changes?since=N` returns pages of `{file_id, encrypted_path, version, revision, ciphertext_hash, deleted}` plus `latest_revision` and `has_more` (`api.ts:27-41`). Upload is `POST uploads` for a presigned R2 PUT URL, `fetch` PUT of the whole encrypted blob, then `POST commit {file_id, base_version, encrypted_path, size, ciphertext_hash, blob_key, deleted?}`, refused with `version_conflict` when `base_version` is stale (`api.ts:121-128`, `sync.ts:676-687`). Downloads are presigned in batches of 100 and fetched 8 at a time (`sync.ts:246-296`). The commit is serialised per vault by a row lock on the server (comment at `sync.ts:581-585`).

**Identity** is a client-generated `crypto.randomUUID()` per file (`sync.ts:664`). Paths are encrypted with a random IV (`crypto.ts:70-73`), so the server cannot compare or enforce path uniqueness.

**Cycle** (`sync.ts:165-200`): pull the whole change feed from the cursor, then push by scanning `vault.getFiles()` and comparing `mtime`+`size` against an index kept in `data.json`, hashing and uploading anything that changed. Deletions are inferred: "anything indexed but no longer on disk was deleted locally" (`sync.ts:635-657`). Optional second pass for the config folder through the adapter (`configstore.ts`).

**Triggers** (`main.ts:103-115`): `vault.on(create|modify|delete|rename)` debounced 5 s, plus a fixed interval (default 300 s), plus a manual command. A request that arrives mid-cycle sets `pendingSync` and re-runs once afterwards, with exponential backoff only when the previous cycle had errors (`main.ts:155-164`, `217-225`). There is no mobile-specific code at all (no resume, visibility, or background handling; `Platform` is used only to label the device and error reports, `main.ts:353-360`).

**Conflicts** (`sync.ts:364-406`): if the local file differs from both the index and the incoming version, `.md`/`.txt` under 2 MiB are three-way merged with `node-diff3` against a "shadow base" (the last-synced plaintext, stored per `file_id` under the plugin folder via the adapter, `basestore.ts`). The **default** mode writes git-style `<<<<<<<` markers into the note on overlap (`settings.ts:50`, `merge.ts:49-58`); the other mode writes a `Name (conflict YYYY-MM-DD HHMM).md` copy (`util.ts:26-37`). Binary and `.canvas` always get a copy. Edit beats delete (`sync.ts:553-560`).

**First sync of an existing vault / merging two non-empty vaults**: there is no special path. Linking to a server vault with an empty index replays from cursor 0: remote files missing locally are written, identical ones are adopted, and every same-path file that differs becomes a conflict copy (no index entry means no merge base, `sync.ts:364`, `371`); then every local-only file is uploaded. The one refinement is 1.0.18's `adoptVaultState` (`sync.ts:40-50`, commit `4eae7e8`): re-linking the **same** vault keeps the index instead of wiping it, after users got a conflict copy for every file on log-out and log-in.

## 4. Ideas worth adopting

1. **Gate on the directory's lint rules locally** (lands in M9 and `scripts/check.sh`). Obsyncian learned each rule by failing a release: 1.0.1 addressed a batch of automated findings (`53b7253`), 1.0.14 was blocked by an **error** (`f31a128`: "Flagged by Obsidian's automated plugin review as an Error, which failed the 1.0.13 release check"), 1.0.18 cleared nine more (`411781c`). Every release is re-reviewed, not just the first. Run `eslint-plugin-obsidianmd`'s `recommended` config over the plugin sources in CI, fail on errors, and keep a written ledger of accepted warnings with reasons, as `411781c`'s commit message does.
2. **Keep a justification ledger for deliberate deviations.** Obsyncian kept `fetch` for blob streaming and whole-vault enumeration, stated why in two commit messages (`53b7253`, `411781c`), and was published. Warnings do not block publication; only errors do ("your plugin won't be installable from within Obsidian until any errors from the automated review are resolved", docs.obsidian.md/plugins/releasing/submit-plugin). Our equivalents: `fetch` of resource URLs for streamed reads (`basalt:client/src/plugin/vault.ts:423`, `:464`) and adapter-level preserving writes (63 adapter calls in `basalt:client/src/plugin/vault.ts`).
3. **Register vault event listeners unconditionally inside `onLayoutReady`, never gated on "is paired"** (M2 task 7). Their bug `4e8ff8d`: `onLayoutReady` fires once per session, so a user who installed and paired without restarting never got listeners or the timer. Basalt already registers inside `onLayoutReady` (`basalt:client/src/plugin/main.ts:404-411`); check that nothing in the pairing path gates it.
4. **Classify server refusals into per-file permanent, account-wide, and transient** (M2, alongside §4.9). Their `file_too_large` is cached per path keyed to `size`+`mtime` until the file changes or the user presses Sync now (`sync.ts:97`, `138`, `609-613`); `quota_exceeded` halts the whole push and pauses auto-sync (`sync.ts:601-608`, commit `b8dc426`). Before that, one oversized file produced "thousands of doomed upload attempts" (`bf2b5d4`). Trew has no quota, but it has `badpath` and size limits: make sure a permanently refused path is not retried every pass (Basalt's stranded list probably already does this; verify with a test).
5. **Disclose in the README in the directory's own terms** (M9 README task). Their "Disclosures (per Obsidian developer policies)" section maps one-to-one onto the policy's list (account, payment, network use, closed server, telemetry). Ours is short: no account, no payment, network use is only the server the user configures, the server reads note contents in plaintext (PLAN §3.6), no telemetry.

## 5. Gotchas and platform quirks they discovered

- **The community directory has replaced `obsidian-releases` PRs.** `gh pr list -R obsidianmd/obsidian-releases` now fails with "Pull requests are disabled for this repository"; the repo is a bot-updated mirror ("chore: Mirror community plugins and themes"). Historical review threads for every sync plugin are no longer reachable through the API. Submission is: sign in at community.obsidian.md, link GitHub, add the plugin; the directory reads `manifest.json` at HEAD of the default branch and reviews automatically.
- **A manifest version with no matching release gets you de-listed.** `obsyncian:release.mjs:5-6`: "Bumping the version without publishing that release is what got us de-listed". Obsidian installs from the release whose tag equals `manifest.json`'s `version`, with no `v` prefix.
- **Manifest rules enforced by the linter** (`eslint:lib/rules/validateManifest.ts:20`, `:245-262`): `id`, `name` and `description` must not contain "obsidian" or "plugin" (case-insensitive substring); the description must be 10 to 250 characters, start with a capital, end with a period, and match `^[A-Za-z0-9\s.,!?'"-]+$` (no colons, semicolons, parentheses, slashes, emoji). The docs add: id unique and without "obsidian". **Basalt's current description, "Fast, secure, self-hosted sync for Obsidian. Simple setup." (`basalt:manifest.json`), fails the forbidden-word check.** Obsyncian's own description contains a semicolon and would fail the character check; it is a warning, so it shipped.
- **Trademark similarity is judged fuzzily on the display name.** `60300ed`: "automated review flags fuzzy similarity to the Obsidian trademark", so "Obsyncian" became "Syncian" in the listing while the id stayed `obsyncian`. "Trew" is not near "Obsidian"; no action, but pick the display name before first submission because the id is permanent (`d470fbb`: "permanent once listed").
- **Rules that are errors (block installation):** `no-plugin-as-component` (passing the plugin to `MarkdownRenderer.render`), `no-view-references-in-plugin`, `no-unsupported-api` (API newer than `minAppVersion`; forced their bump to 1.7.2, `53b7253`), `detach-leaves`, `no-forbidden-elements`, `no-static-styles-assignment`, `platform` (navigator-based OS detection), `regex-lookbehind`, `settings-tab/no-manual-html-headings`, `settings-tab/no-problematic-settings-headings`, `sample-names`, `no-sample-code`, `no-eval`, `no-unsanitized/*` (the `innerHTML` family), and **`no-console` for anything other than `warn`, `error`, `debug`** (`eslint:lib/index.ts:134-224`). The rest are warnings: `prefer-window-timers`, `no-global-this`, `hardcoded-config-path`, `prefer-file-manager-trash-file`, `no-tfile-tfolder-cast`, `vault/iterate`, `commands/*` (no default hotkeys, no plugin id in command id, no plugin name in command name), `ui/sentence-case`, `validate-manifest`, `validate-license`, `no-nodejs-modules` (off when `isDesktopOnly`), and `no-restricted-globals` for `fetch`, `localStorage`, global `app`. The config extends `typescript-eslint`'s `recommendedTypeChecked`, which is why Obsyncian also had to fix floating promises, unsafe `any`, non-Error rejections and deprecated APIs (`53b7253`), and a dependency in `esbuild.config.mjs`.
- **Basalt code that trips the review today**, checked against `664a963`: `console.info` in `basalt:client/src/plugin/main.ts:937`, `:1666`, `:1743`, `:1878` (**errors**); bare `setTimeout` at `main.ts:917`, `:1153`, `visible-poll.ts:24`, and `globalThis` at `visible-poll.ts:9`, `main.ts:2889`, `:3702`, `:4978`, `vault.ts:278` (warnings); `fetch` at `vault.ts:423`, `:464` (warning, justify). No `innerHTML`, no HTML headings in settings (uses `setHeading()`, `main.ts:4084`, `:4121`), no default hotkeys, command ids and names clean, `navigator` used only for the clipboard (`activity.ts:239`).
- **Client-side telemetry is forbidden outright** by the developer policies ("Plugins and themes must not ... Include client-side telemetry"); only server-side telemetry is a disclosure. Obsyncian ships an opt-out error reporter, on by default (`settings.ts:53`, `main.ts:233-238`), and its README says "The plugin sends no telemetry". It passed the automated review, so this is enforced by humans on report, if at all. Do not rely on that.
- **`fetch` needs CORS; `requestUrl` buffers.** They send blob bytes with `fetch` because `requestUrl` "can't stream large bodies" and configured the R2 bucket's CORS for Obsidian's origins (`api.ts:138-150`). Relevant to us only for plain HTTP endpoints; the WebSocket is not subject to CORS, but the server's origin allow-list must include desktop and Capacitor origins (Basalt's `http.go` origin patterns already exist).
- **`Vault.trash` versus `FileManager.trashFile`:** the review wants the latter because it respects the user's deletion preference (`53b7253`, `sync.ts:554-555`).
- **A synchronous run of cheap iterations starves the renderer.** Self-echo and unchanged-file checks never await real I/O, so status text updated in the DOM but never painted; `await Promise.resolve()` is not enough, a `window.setTimeout(0)` macrotask is (`sync.ts:115-122`, `d692d8e`). Worth knowing for Basalt's settled-pass progress display.
- **Files Obsidian cannot create still exist in vaults** (made in Finder or Explorer) and sync up fine from their origin device, but no other device can write them (`util.ts:44-50`, `0d425a5`). They skip them before downloading so the blob is not re-fetched every cycle (`sync.ts:256-272`).
- **Popout windows:** `window.setTimeout` rather than the bare global so timers resolve against the right window (`sync.ts:117-121`, `411781c`).

## 6. Their bugs or weaknesses we must not repeat

1. **A failed download is skipped forever** (rule 2, "A failed read is not an empty result"). `pull()` advances the cursor past every change regardless of outcome (`sync.ts:213-219`), and `applyRemoteChange` returns silently when the blob is missing because presign or fetch failed (`sync.ts:343-344`). One timeout on a large attachment and that version never arrives. If the user then edits the stale local copy, every push is refused as `version_conflict` (`sync.ts:598-600`) and no later pull re-fetches, because the cursor is already past it: a permanent loop reported as "deferred". Any exception in apply (decrypt, a write refused by the OS) has the same effect.
2. **Excluded changes are consumed, not deferred** (rule 7, "A status describes the vault, not the filter"). Changes under an excluded folder return early and the cursor still advances (`sync.ts:323`). Removing the exclusion later never pulls what arrived meanwhile. They noticed this for the config toggle and rewind the cursor to 0 when it is enabled (`settings.ts:244-253`), but not for folder excludes.
3. **Duplicate identities for one path.** New files get a random UUID (`sync.ts:664`), the index is persisted only after pull pages and at the end of the cycle (`sync.ts:180`, `198`, `233`; nothing in `push()`), and the server cannot see paths. A crash or a mobile OS kill during a first upload re-uploads every committed-but-unsaved file under a fresh UUID. Two devices creating the same path offline (daily notes are the textbook case) produce two live `file_id`s at one path; each device then indexes both, `byPath` keeps one (`sync.ts:568-569`), and a later delete removes only one, so the other resurrects. No test covers concurrent creation at one path (`test/sync.test.ts`). Our design keys on the path with conditional `base`/`prevBase` writes on the server, which refuses the second create as stale. **We are right**, and this is the argument for keeping path-keyed conditional writes if anyone proposes client-generated ids.
4. **Deletion inferred from absence** (rule 6, "Deletions are entries, not absences"). Anything indexed and missing from `vault.getFiles()` is deleted on the server (`sync.ts:635-657`). Any moment where the listing is incomplete (early startup, a folder moved out and back, a mount hiccup) becomes a remote delete that propagates to every device. They guard excluded and config paths, nothing else.
5. **Oversized files vanish silently** (PLAN §4.9). `pushFile` returns without a report for anything over 200 MB (`sync.ts:661`). Everything under it is read whole into memory, encrypted into a second copy, and PUT in one request (`sync.ts:668-679`); with a 120 s timeout (`api.ts:66`) a 250 MB file on a phone uplink below about 2 MB/s can never succeed and is retried every cycle, and because `withTimeout` does not abort (`api.ts:68-81`) the old upload keeps consuming bandwidth.
6. **Check-then-write with no compare-and-swap.** The local file is read and hashed, the merge or decision is computed, then written with `vault.modifyBinary` (`sync.ts:349-375`, `794-802`). An edit that lands in between is overwritten. No `vault.process`, no editor awareness. Basalt's `process()`-based preserving replace (`basalt:client/src/plugin/vault.ts:988`) is the fix; keep it.
7. **Remote renames rewrite links locally.** A pure remote rename is applied with `fileManager.renameFile` (`sync.ts:336`), which runs Obsidian's link updater on this device, although the originating device's link rewrites arrive as their own edits. It usually converges because both rewrites are byte-identical, but it creates local edits the sync did not intend and races with the incoming ones. Basalt applies renames with `adapter.rename` (`basalt:client/src/plugin/vault.ts:900`, `:1089`), which is right for a sync applier.
8. **Conflict markers written into notes by default.** The default mode writes git-style markers on overlap (`settings.ts:50`), including inside YAML frontmatter, where they break every property and Dataview query until someone cleans up, and the marked text is then synced everywhere. Their README still says "Nothing is merged" (`README.md`, FAQ), which is out of date. Keep-both remains the right default (PLAN §4.6).
9. **Settings, credentials, passphrase and the whole index in one `data.json`** (`main.ts:343-345`). Every save rewrites all of it, and a torn write loses the device token along with the index. Basalt's separate `index.json` with a journal is better; do not merge them during the strip.
10. **The error reporter leaks what it promises not to.** The setting says reports never include file names (`settings.ts:216`), but `report.errors` is built from strings like `push ${file.path}: ...` and `delete ${path}: ...` (`sync.ts:613-615`, `655`), and the first five are sent to the server (`main.ts:188-191`). For an E2EE user that is plaintext paths leaving the device, against both the product's claim and the directory policy.
11. **Smaller:** the sync interval is captured once in `onLayoutReady` (`main.ts:112-114`), so changing it needs a restart; the plugin's own writes fire `modify`, which queues an extra no-op cycle after every pull (`main.ts:108-111`, `155-163`).

## 7. Where they contradict our plan, and who is right

| Topic | Obsyncian | Trew plan | Who is right |
|---|---|---|---|
| File identity | Random client UUID, server blind to paths | Path, with conditional writes on the server (PLAN §3.4, `plan/protocol.md`) | **We are.** Their design cannot detect concurrent creation at a path (§6.3). |
| Transport | HTTP polling of a change feed every 5 min plus debounced events | WebSocket with live fan-out | **We are**, for one person's devices. Their choice is driven by cheap hosting (bytes never touch their servers), not correctness. |
| Bodies | Whole-file blobs, 200 MB cap, in memory | Content-defined chunks, streamed (PLAN §2.2) | **We are.** §6.5 is what whole files cost on a phone. |
| Deletes | Inferred from absence | Deletions are entries (rule 6) | **We are.** |
| Conflict default | Inline markers | Keep both versions | **We are.** Markers mutate user content, and the frontmatter case is bad. |
| Config folder sync | Optional, opt-in | Refused (PLAN §1) | Both defensible. Their implementation shows the costs: a second code path, a second deletion scope with its own guard (`sync.ts:638-642`), and cursor rewinds. The refusal stands. |
| Adapter versus Vault API | Vault API for notes, adapter only for config and bases | Adapter-level preserving writes (reuse map: plugin `vault.ts` unchanged) | **We are** on durability. The guideline "Prefer the Vault API over the Adapter API" is advice, not a lint error. Record the reason once and be ready to explain it if a human reviewer asks. |
| Error reporting | Opt-out, on by default | None | **We are.** It is forbidden client-side telemetry, and theirs leaks paths. |
| Platforms | Every platform, no special handling | macOS, Linux, Android; no Windows (PLAN §1; iOS unstated) | Neither yet. Once listed, the plugin installs anywhere. PLAN has to say what happens on Windows and iOS (§8). |
| Self-update | Removed for the listing (`d470fbb`: "community directory policy forbids self-updating plugins") | `trew update` for the Go binary (M9) | Compatible, as long as self-update stays a server-binary feature and the plugin never downloads code. |

## 8. Concrete recommended changes to PLAN.md

- **M9: add "Community directory submission" as its own task**, with: (a) `eslint-plugin-obsidianmd` `recommended` config wired into `scripts/check.sh` and CI over `client/src/plugin` and every `client/src/core` file the plugin bundles, failing on errors; (b) `docs/development.md` gets a ledger of accepted warnings with reasons (`fetch` for streamed resource reads, adapter-level preserving writes, whole-vault enumeration); (c) the step-by-step submission flow (sign in at community.obsidian.md, link GitHub, add the plugin) with the note that every release is re-reviewed and that an error makes that release uninstallable.
- **M2 task 7, add:** replace the four `console.info` calls in `basalt:client/src/plugin/main.ts` (937, 1666, 1743, 1878) with `console.debug` or the activity log; they are lint **errors** under the directory review. Switch bare `setTimeout` to `window.setTimeout` (`main.ts:917`, `:1153`, `visible-poll.ts:24`) and replace `globalThis` reads with `window`/`activeDocument` where possible, since both are warnings that are cheap to clear.
- **M9 manifest:** state the manifest rules in the plan: `id`, `name`, `description` free of "obsidian" and "plugin"; description 10 to 250 characters, capitalised, ending in a period, only letters, digits, spaces and `.,!?'"-`. Basalt's description fails; propose "Sync your vault through a server you run, with a built-in endpoint for AI agents." Decide the display name before first submission, since the id is permanent once listed.
- **M9 release workflow:** one script or workflow that bumps `manifest.json` and `versions.json` and publishes the matching `X.Y.Z` GitHub release with `main.js`, `manifest.json`, `styles.css` in one step, refusing to leave either without the other. Obsyncian was de-listed for exactly this gap. Note that `server/vX.Y.Z` releases in the same repository must not be the only release after a manifest bump.
- **§1 scope, or a new §4.12 "Platforms the listing reaches":** a listed plugin installs on Windows and iOS whatever the plan refuses. Decide the behaviour: refuse to pair on `Platform.isWin` with an explanation in the panel and the README (preferred, given the plan's reasons), and state iOS's status explicitly, since §1 lists macOS, Linux and Android and says nothing about it.
- **M9 README:** add a "Disclosures" block in the directory's own vocabulary: no account, no payment, network use limited to the configured server, the server stores notes in plaintext and the MCP endpoint exposes them to the agent's model provider, no telemetry of any kind. Add to §3.6 a line that the plugin never adds client-side error reporting, because the policy forbids it.
- **§8 or M2 tests, add regression cases drawn from §6:** (a) a download that fails mid-pass leaves the change pending, not consumed; (b) un-ignoring a folder pulls what arrived while it was ignored; (c) two devices creating the same path offline end with one path identity and both contents; (d) a process kill during a first upload does not duplicate any path; (e) an incomplete listing never produces a remote delete. Basalt probably already holds most of these; the point is to find the tests that carry them before the strip and keep them (PLAN §2.1).
- **§2.3.1 or M2, note:** keep device credentials out of the file that holds the index. Basalt already separates `data.json` from `index.json`; say that the strip must keep that separation.
- **`plan/ideas.md`, "Obsidian config sync" entry:** add the plugin-folder, `workspace.json` and `workspace-mobile.json` exclusions and the cursor-rewind problem as known costs, citing `obsyncian:src/main.ts:58-62` and `src/settings.ts:244-253`, so any revisit starts from them.
